# 模块化策略

## 目标

保持一个主仓库，通过职责目录、独立 CMake target 和稳定接口实现内部模块化。结构参考
`zelos/znavigator` 的薄入口和小型 target，但不照搬动态插件、复杂构建兼容和大型组织层级。

## 分层

```text
cockpit-system/
├── cockpit/
│   ├── apps/       用户应用
│   ├── core/       通用基础设施
│   ├── drivers/    Linux/硬件适配
│   ├── modules/    平台无关领域能力
│   ├── proto/      跨进程契约
│   └── processes/  进程入口与依赖装配
├── tools/          诊断和模拟器
├── tests/          单元与集成测试
└── scripts/        构建、运行和部署脚本
```

依赖方向：

```text
apps / processes / tools
          ↓
       modules
          ↓
       drivers
          ↓
         core
```

实际依赖按接口决定，禁止反向依赖：

- `core` 不依赖业务模块。
- `modules` 不依赖 process 或 app。
- `drivers` 只适配硬件接口，不包含业务策略。
- UI 不直接打开硬件设备。
- process 之间通过 `cockpit/proto` 定义的 gRPC 契约或明确 IPC 通信，不直接 include 对方实现。

## core

只存放跨领域基础设施：

- `config`：类型化配置。
- `event`：进程内事件。
- `ipc`：共享内存映射等通用 IPC。
- `logging`：日志。
- `runtime`：参数、信号和模块生命周期。
- `time`：主机时间戳。

禁止把暂时不知道放哪里的代码塞进 `cockpit/core/common/base/misc`。

## modules

领域代码必须能在没有长运行进程和真实硬件时测试。

```text
cockpit/modules/audio/
  frames/ capture/ vad/ playback/ wav/

cockpit/modules/camera/
  frames/ capture/ shared_memory/

cockpit/modules/voice/
  asr/ tts/ assistant/ actions/ responses/
```

领域子目录用于表达真实职责，由领域根目录的 `CMakeLists.txt` 集中声明 target。只有需要独立复用、
依赖隔离或条件编译的能力才建立 target，不为一两个文件机械增加叶子级 CMake 文件。调用方链接满足
需求的最小 target。

`can`、`vehicle` 等文件较少且职责单一的模块保持扁平，不为了目录对称而硬拆。

## processes

process 表示部署、资源所有权和故障隔离边界，不等于云端微服务。Linux 上仍由 systemd `.service`
unit 托管，protobuf 中仍可使用 Service 描述 RPC 契约。

只有满足以下条件之一才建立独立进程：

- 独占硬件设备。
- 需要故障隔离。
- 有独立生命周期。
- 有真实部署边界。

当前进程：

- `vehicle-data-service`
- `cockpit-gateway-service`
- `audio-service`
- `camera-service`
- `voice-interaction-service`
- `cloud-uplink-service`（占位）

VAD、ASR adapter、intent parser 等优先作为进程内模块，不单独创建进程。

复杂进程可按职责拆目录：

```text
cockpit/processes/audio/
  capture/ processing/ playback/ grpc/

cockpit/processes/camera/
  preview/ control/ grpc/

cockpit/processes/interaction/
  interaction/ audio/ vehicle/ hmi/ grpc/
```

`main.cc` 只做配置读取、依赖装配、启动和退出。

`ProcessRuntime` 管理单进程基础生命周期；`ModuleManager` 只接收具有明确启动、停止、依赖或线程
生命周期的组件。不要为了统一形式把纯数据类、解析函数或同步业务对象包装成 Module。

生产启动组合由 systemd target 表达：`cockpit.target` 是核心进程，`cockpit-development.target`
增加研发录包，`cockpit-cloud.target` 单独启用云端进程。不增加与 systemd 重复的通用 launcher。

## CMake target

命名使用简短职责名：

```text
config logging runtime ipc
audio_frames audio_capture audio_vad audio_wav
camera_frames camera_capture camera_shm
voice_asr voice_tts voice_actions
```

避免 `cockpit_common_runtime` 这类冗长名称。每个 target 声明自己的直接依赖，不依赖全局 link
状态。

## 通信规则

- 同线程：函数调用。
- 同进程低频：callback/EventQueue。
- 音频连续流：SPSC RingBuffer。
- 相机大帧：shared memory。
- 控制、状态和文本：gRPC。
- 云端：未来 MQTT/WebSocket。

不把 PCM、图片或未来点云直接放进 gRPC。

## 何时增加抽象

只有至少两个真实调用方出现相同需求时，才增加通用 Actor、MessageBus、Scheduler、Recorder、
Monitor 或插件框架。不要先创建空接口等待未来使用。

模块边界不等于把每段短逻辑做成 helper 或类。单次、短小且没有独立资源/协议边界的逻辑优先留在
调用处；具体判断标准见 [代码风格.md](代码风格.md) 的“克制抽象”。

## 何时拆仓

当前只维护 `cockpit-system`，负责 Jetson 车端车辆、音频、语音、相机、UI、诊断和部署。完整云
平台、生产 Web 前端、车队管理、自动驾驶算法、Android 虚拟化和量产级安全不属于当前范围。

只有同时出现以下条件时才考虑拆仓：组件可独立部署、具有独立版本周期、跨仓协议稳定、维护责任或
技术栈明确，并且独立 CI/CD 的收益高于同步成本。未来可能形成 `cockpit-cloud`、`cockpit-web`，
`cockpit-proto` 只有在协议真正稳定后才可能独立；现阶段不创建空仓库。

如确实需要历史展示，云端先保持最小范围：接收车辆状态、保存 SQLite/PostgreSQL、查询最近状态和
历史曲线、提供简单设备鉴权，不直接建设完整车联网平台。真实部署边界决定仓库边界。
