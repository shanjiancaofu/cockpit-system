# 代码风格说明

本项目的 C++ 风格严肃参考 `zelos/znavigator` 和 `zelos/zcarcloud`，但不照搬其公司内部版权头、私有
pre-commit 源、Bazel 历史配置或 zlog/zutil 私有依赖。

## 基础规则

- C++ 源文件使用 `.cc`，头文件使用 `.h`。
- clang-format 基于 Google style，列宽 100，指针左贴，短函数和 lambda 不压成单行。
- namespace 使用多层展开写法，不使用 C++17 nested namespace 简写。
- include 分组顺序参考 zelos：系统头、第三方头、项目头；项目内 include 使用 `cockpit/...` 绝对路径。
- C++ 文件名统一使用 `snake_case`；类名保持 `PascalCase`，target 使用简短的小写名称。

## 目录与构建

- 顶层产品源码按 `apps / processes / modules / drivers / core / proto` 分层。
- 一个可执行程序使用一个目录，内部默认平铺；只有形成明确子域时才增加子目录。
- 领域源码目录可以表达职责，但不要求每个源码子目录维护独立 `CMakeLists.txt`。
- 只有需要独立复用、依赖隔离或条件编译时才建立 target；领域入口统一声明所属 target。
- 多命令工具参考 `topic`：入口与命令实现分离；命令源码默认直接属于可执行 target，只有
  被其他程序复用、需要独立依赖隔离或直接单元测试时才建立 commands target。
- service 不能包含供其他 service 引用的公共代码；共享 client/contract 放入对应领域 module。

## 类接口

- public 生命周期和外部接口放前面，private helper 和成员变量放后面。
- 不可拷贝类使用 `COCKPIT_DISALLOW_COPY_AND_ASSIGN(TypeName)`，风格对应 zelos 的
  `DISALLOW_COPY_AND_ASSIGN`。
- 析构函数需要表达生命周期语义：持有线程、文件、socket、共享内存、gRPC server 的类必须在析构或
  `Stop()/Shutdown()` 中释放资源。
- 简单数据结构使用 `struct`，默认成员初始化；有不变量或资源生命周期时使用 `class`。

## 克制抽象

优化代码的目标是降低理解成本，不是增加函数、类、接口或文件数量。短逻辑默认留在使用位置；不要
为了“看起来整洁”把几行顺序代码拆成只调用一次的辅助函数，也不要用一个新的薄封装替换刚删除的
薄封装。

增加辅助函数、类或接口前，至少满足以下一项：

- 当前已有两个及以上真实调用方，并且抽取后确实消除了重复逻辑。
- 隔离了复杂算法、资源生命周期、线程边界、协议转换或第三方依赖。
- 表达了稳定的业务概念或模块边界，调用者不需要了解内部细节。
- 可以独立测试，并且该独立测试覆盖了有意义的不变量或异常路径。
- 抽取后明显降低了调用者的分支、状态或错误处理复杂度。

以下情况默认不抽取：

- 只调用一次的字段赋值、简单条件、字符串拼接或纯转发。
- 函数体只是调用另一个同签名函数，既不转换语义，也不管理资源。
- 为未来可能出现的调用方预建 factory、provider、manager 或接口。
- 仅通过换名字隐藏原本一眼可读的表达式，导致阅读者必须跨文件或上下跳转。
- 为追求“零重复”制造额外状态、模板或继承关系；少量显式重复比错误抽象更容易维护。

单次调用不是绝对禁令。解析器、校验算法、复杂清理流程和线程入口即使只有一个调用点，只要形成
清晰边界并降低主流程复杂度，也可以保留。判断时不按固定行数，而是比较修改前后的符号数量、跳转
次数、状态共享和测试价值。

Review 新抽象时依次确认：当前有几个调用点；删掉后能否在原位置清楚表达；是否隔离了真实复杂度；
是否引入新的所有权或状态；能否用更少的概念完成同一件事。答案不充分时，优先就地实现。

## 错误处理

- 底层模块优先返回 `bool`，通过 `std::string* error` 输出错误原因，避免在实时路径抛异常。
- 进程启动、配置加载、文件系统初始化等非实时路径可以使用异常，但要在服务边界转成日志和非 0 退出码。
- 弱依赖失败只记录 warning，不阻断主流程；强依赖失败应返回错误或进入 faulted 状态。

防御性检查只放在不可信边界：用户输入、配置和文件内容、外部 API、数据库读取结果、跨进程或跨团队
接口。边界处检查格式、范围、大小、空值、版本和资源状态，并把错误转换成当前模块可理解的结果。

边界需要校验，不代表校验必须抽成 helper。先决定是否需要检查，再判断代码是否存在真实复用、复杂
解析、协议转换或资源清理边界；一次简单范围判断和错误返回应留在调用处。不能用“这是外部输入”替
无复用的薄函数、validator 类或 manager 层辩护。

以下值默认可信，不重复防御：hardcode 常量、同一函数内部刚生成并立即传递的值、枚举和类型系统已经
保证的不变量、构造函数完成后由类自身维护的状态。不要为这些值增加永远不会触发的分支、fallback 或
薄校验 helper。若内部不变量可能被破坏，应修正所有权或类型表达；需要调试断言时使用断言，不伪装成
运行期错误恢复。

## Runtime 与服务边界

- `core/runtime` 只放生命周期、依赖图、模块编排等通用运行时能力，不放车辆、音频、相机、语音业务。
- `library/*` 是进程级业务装配和资源所有权边界；平台无关的可复用逻辑放到 `modules/*`。
- 长运行产品业务只由 Navigator 启动，不再为模块增加独立 service main；一次性诊断工具保留自己的入口。
- 同进程低频事件用 `MessageBus`；大块数据不走 MessageBus/gRPC，使用 shared memory 或文件句柄。

一次性工具的 `main.cc` 负责 `ProcessRuntime` 创建、业务动作装配和统一结束；不建立只把
`argc/argv` 原样转发给 `Run()` 的薄入口。业务文件使用 `ProbeAudio`、`ControlCamera`、
`SimulateCan` 等能表达领域动作的入口，并接收已初始化的 Runtime；不在每个错误分支重复调用
`MarkStopped()` 或增加 `Finish(runtime, result)` 转发 helper。

## 工具

- `CPPLINT.cfg` 保持与 zelos 一致的核心过滤项，当前不把 cpplint 放入普通 pre-commit，因为开发环境
  未默认安装 cpplint。
- 普通提交执行 pre-commit 基础检查和 clang-format；clang-tidy 保持 manual，按模块分批清理。
