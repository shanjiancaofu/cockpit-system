# Cockpit 机器人系统技术文档

更新时间：2026-08-19

本文是 `cockpit-system` 当前机器人/车机方向的权威方案文档。它吸收
`docs/example/` 中的硬件分层、导航、TF、视觉流水线和离线部署经验，但只记录当前仓库
能够承接的接口、边界和后续实施计划。`docs/example/` 中的课程材料和旧方案保持原样，
不作为当前代码、模型、依赖或验收结果。

## 1. 当前定位

项目目标是运行在 Jetson/Linux 上的离线机器人车机系统原型：Jetson 负责感知、导航、
语音 Agent、用户界面和系统管理；STM32 负责实时底盘、传感器采集和安全保护。

当前不是量产 QNX + Android 座舱，也不宣称已具备 Android Automotive、QNX BSP、
Android App 容器或商业地图/音乐 App 运行环境。Qt/QML 是当前 Jetson 端的用户界面原型，
后续可以迁移为量产座舱的上层交互参考。

## 2. 系统分层

```text
STM32 下位机
├─ 电机 PWM、编码器、PID、心跳失联保护
├─ SR501 人体感应采集
├─ 哨兵相关硬件状态
└─ 后续确定的 UART/CAN 协议
          │
          ▼
Jetson Orin Nano / Linux
├─ cockpit-navigator：唯一长运行入口和模块监管
├─ vehicle / audio / camera / recording modules
├─ Voice Agent：KWS、VAD、ASR、LLM、TTS、确定性动作路由
├─ Qt 6/QML：仪表、中控、相机、语音、设置和应用入口
├─ ROS 2/Nav2 bridge：后续独立进程
└─ 诊断、日志、资源和升级管理
```

### 2.1 Navigator 与模块

`cockpit-navigator` 通过固定 mode、版本化 C ABI、模块子进程和本地 IPC 管理业务模块。
driver 持有硬件，UI 和 Agent 只通过 gRPC/本地接口访问能力。异常退出、健康检查、重启
限制、进程组清理和诊断快照由 Navigator 负责。

### 2.2 STM32 边界

STM32 不依赖 Jetson 的 AI 推理时延。Jetson 断连时，STM32 继续执行底盘安全策略并在
心跳超时后停止运动输出。SR501 接在 STM32 下位机，Jetson 不直接读 GPIO；Jetson 后续只
接收标准化的 `motion_detected`、`motion_cleared`、`sensor_fault` 和 `sentinel_state` 等
状态/事件。

CAN 帧、DBC、信号定义、心跳和故障码等到真实 STM32/收发器联调时确定。当前 vcan/CAN
测试只证明软件边界和报文处理能力，不代表真实总线已完成。

## 3. 当前已落地能力

- Navigator 统一启动、停止、健康检查、崩溃恢复和有限重启。
- V4L2/GStreamer/合成相机采集、共享内存最新帧、预览、拍照和故障恢复。
- 音频采集、16 kHz mono 算法输入、24 kHz Kokoro 原生输出和有界播放队列。
- Sherpa KWS、Silero VAD、SenseVoiceSmall INT8 和 Kokoro provider 的 Ubuntu x86_64 smoke。
- llama.cpp b10456 托管、Qwen3.5-2B/4B GGUF、SSE、首 token/总超时、取消和进程重启。
- `TranscriptNormalizer -> DeterministicCommandRouter -> allowlisted ActionDispatcher` 安全边界。
- Qt 6/QML Dashboard、Camera、Diagnostics 原型及 `open_camera` HMI 动作桥接。
- Ubuntu x86_64 的固定录音、TTS、相机、语音服务和基础并发验证。

具体完成度和证据以 [实现状态](实现状态.md)、[项目进度总览](项目进度总览.md) 和
[变更记录](变更记录.md) 为准。

## 4. 用户车机 UI 方向

参考 `docs/example/picture/` 的信息密度和视觉层次，当前 Qt/QML UI 应从工程诊断面板
升级为面向用户的车机界面：

```text
主界面
├─ 顶部状态栏：速度、连接、时间、电量/电源、告警
├─ 主视觉区：地图/导航或相机内容
├─ 浮层：下一步导航、语音状态、媒体状态
├─ 底部 Dock：主页、地图、媒体、相机、语音、设置
└─ 二级页面：诊断、设备、哨兵、应用管理
```

设计要求：驾驶中优先显示速度、告警和导航；设置、诊断和开发信息不放在首页；统一
深色主题、较大触控目标、清晰的状态颜色和故障降级提示。UI 不直接访问 V4L2、ALSA、
GPIO、CAN 或 ROS。

### 4.1 第三方 App 边界

微信、网易云音乐、商业地图等不是当前 Ubuntu 原生能力。先实现受控 `AppLauncher` 概念：

```text
Qt 应用入口
  -> allowlisted app descriptor
  -> native Linux / Android bridge / projection backend
  -> running / unavailable / failed 状态
```

禁止 UI 通过任意 shell 启动程序。当前阶段可实现本地媒体播放器和应用入口状态；真正的
Android APK 运行需要 Android Automotive、Android 容器或独立手机投屏方案，需另行确定
硬件、窗口合成、音频焦点、权限和生命周期合同。

## 5. 语音与离线 AI 基线

```text
16 kHz mono microphone
 -> KWS / VAD / complete speech segment
 -> SenseVoiceSmall INT8
 -> deterministic router or local LLM
 -> Kokoro 24 kHz mono PCM
 -> Audio Driver / physical device rate
```

- 算法输入固定为 16 kHz mono；Kokoro 保持原生 24 kHz mono，不做 24→16→48 的有损往返。
- production LLM 为 Qwen3.5-2B Q4_K_M；4B 仅为 comparison profile。
- Qwen3.5 语音请求关闭 thinking，只将 `delta.content` 作为用户可见文本。
- LLM 不能发送 CAN、执行 shell、调用任意 RPC 或绕过确定性路由。
- 当前没有等价备用 provider；初始化失败明确 fail-closed，不引入虚假自动降级。

Jetson 的真实性能、温度、功耗、RSS、声学指标和小时级稳定性必须在目标设备实测，
Ubuntu x86_64 结果只能作为功能基线。

## 6. ROS 2 与导航 Bridge

ROS 2/Nav2 不直接链接进 Navigator 核心，采用独立 bridge：

```text
Navigator / Agent / UI
        <-> Unix socket 或 gRPC
独立 ros2_bridge 进程
        <-> ROS 2 topics / services / actions
        <-> Nav2 / SLAM / AMCL
```

Bridge 负责导航目标、状态、取消、失败、超时、`frame_id` 和时间戳转换。图像和激光等
高带宽数据使用 SensorDataQoS/有界队列；导航任务使用 Action；控制命令和安全状态使用
可靠的小消息。ROS 类型不得泄漏进 `cockpit/core`、Agent 或 UI 公共接口。

在 ROS2 Humble、Nav2 版本和消息合同确定前，只实现 fake bridge 和接口测试；不要把示例
文档中的 ROS1 Noetic、`move_base` 或 `/asr` Python 节点当作当前实现。

## 7. 哨兵模式

SR501 由 STM32 采集，Jetson 实现业务状态机：

```text
DISARMED -> ARMED -> MOTION_DETECTED -> CAPTURING -> COOLDOWN -> ARMED
```

需要的事件字段：`event_id`、单调时间戳、传感器状态、去抖后的触发状态、固件版本和
故障原因。Jetson 负责相机抓帧/录包、容量上限、事件索引、UI 状态和异常恢复；STM32
负责电平、中断、去抖和硬件故障上报。真实串口/CAN 联调前，先用 fake event fixture 验证
状态机、重复触发、冷却、相机不可用和断电恢复。

## 8. 相机与视觉后续

相机标定和红绿灯识别后置，不阻塞当前语音和车机 UI 主线。

### 8.1 标定

后续增加棋盘格/Charuco 工具、内参/畸变 YAML、相机到 `base_link` 外参、版本和 SHA 校验，
统一通过静态 TF 发布；参数必须在 Jetson 实际安装位置重新标定。

### 8.2 红绿灯识别

后续作为独立 bounded detector，输出 `RED/YELLOW/GREEN/UNKNOWN`、置信度、时间戳和
`frame_id`。视觉结果只能进入感知/导航安全层，不能直接驱动电机或覆盖底盘急停。

## 9. 部署与验收顺序

1. Ubuntu x86_64 持续维护 Debug/Release、ASan/TSan、语音和 Navigator 回归。
2. 在 Jetson 固定 JetPack、Ubuntu、模型/runtime、音频设备和 UI 分辨率。
3. 先验证 STM32 事件/状态接口和哨兵 fake fixture，再做真实 SR501 联调。
4. 重做 Qt/QML 用户车机主界面，加入受控 App Launcher 和本地媒体能力。
5. 固定 ROS2 Humble/Nav2 合同，运行独立 bridge 和导航 fake 测试。
6. 完成 Jetson 真实 KWS/VAD/ASR/TTS/LLM、相机、温度、功耗、RSS 和长稳验收。
7. 最后进行相机标定、红绿灯识别、真实 CAN/DBC 和现场整车联调。

不得把示例文档中的模型、Ollama/Piper 命令、旧 ROS 版本、历史性能数字或图片中的第三方
应用视为当前发布内容。

## 10. 当前执行计划

Qt/QML 用户车机 UI 已建立面向 1280×720 的稳定主框架、驾驶首页、相机、媒体、小山语音、设置、
诊断页面和底部 Dock，并复用 Vehicle、Camera、Health 与 HMI 模型。第二批新增 Voice UI model，
通过本地 gRPC 展示真实会话状态、最新 transcript/回复和错误，并只开放固定中断操作。导航、媒体和
Android 未接入时均明确展示边界；UI 没有把 driver、ROS 或任意 shell 调用带进 QML。

下一实施项是受控 `AppLauncher` 和本地媒体接口，只交付 allowlist、可用状态、生命周期和失败呈现；
在 Android Automotive、容器或手机投屏方案确定前，不承诺运行微信、网易云音乐或商业地图 APK。
随后依次推进 STM32-SR501 fake 哨兵闭环和 ROS2/Nav2 fake bridge。相机标定、红绿灯识别、正式
CAN/DBC 与 Jetson 整机长稳仍按硬件依赖后置。
