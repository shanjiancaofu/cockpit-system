# AIM2 秋招冲刺规划

**定位：嵌入式 Linux / 机器人系统 / 智能座舱方向**  
**核心平台：Jetson Orin Nano 8GB + STM32G474 + ROS2/Nav2 + Camera/Audio/CAN FD + 端侧 AI**  
**阶段目标：从“功能覆盖”转向“真机证据、工程深度、可量化结果、可面试表达”**

---

## 0. 文档结论

AIM2 秋招阶段不再追求继续横向堆功能，而是执行 **“广度 30%，深度 70%”** 的策略：已有功能负责证明系统广度，核心链路负责建立可追问的工程深度。

秋招前最重要的成果不是“又接了多少模块”，而是下面四件事：

1. **完整链路能跑通**：Jetson → Linux/ROS2/AI → CAN FD → STM32 → 底盘。
2. **核心模块有真机证据**：Camera、Audio、CAN FD、LLM、Nav2/LiDAR。
3. **每条核心链路有指标**：延迟、频率、RSS、GPU/CPU、RTF、tok/s、watchdog、恢复时间、长稳时间。
4. **每个简历亮点都能被连续追问 10~15 分钟**：能解释原理、设计权衡、故障、定位过程、修复方案和验证方法。

一句话定位：

> 在 Jetson Orin Nano 与 STM32G474 上实现一套从 Linux 多媒体、ROS2/Nav2、端侧语音 AI 到 CAN FD 实时底盘控制的完整系统，并重点解决传感器接入、通信安全、资源约束、故障恢复和系统性能问题。

## 1. 秋招项目策略：广度够用，主攻深度

### 1.1 广度已经足够

当前项目已经覆盖：

- Linux / C / C++ / CMake / Shell
- Jetson Orin Nano / CUDA
- STM32G474 / FDCAN / PWM / Encoder / PID
- SocketCAN / CAN FD / CRC / heartbeat / watchdog
- ROS2 / Nav2 / TF / LaserScan / CameraInfo
- V4L2 / Argus / ALSA
- gRPC / AF_UNIX / Qt
- Sherpa-ONNX / SenseVoice / Kokoro / llama.cpp / Qwen
- CI / Sanitizer / pre-commit / shell tests

因此，后续不以“再加更多名词”为目标。

### 1.2 秋招需要形成的四条深度主线

#### 主线 A：Jetson ↔ STM32 CAN FD 底盘通信

必须能讲清楚：

- 为什么使用 CAN FD，而不是 UART / classic CAN。
- nominal 500 kbit/s、data 2 Mbit/s、BRS 的作用。
- 0x101 velocity command 的字段、序列号、CRC16-CCITT-FALSE。
- command timeout 与 peer heartbeat 为什么独立。
- duplicate / stale sequence 如何拒绝，基线何时重置。
- ERROR-PASSIVE、TEC/REC、bus-off、ACK、sample point。
- SocketCAN 用户态路径与 STM32G474 FDCAN 对接。
- Nav2 `/cmd_vel` 到 CAN 之前为什么必须有独立 safety adapter。

最终证据：真实 can0 ↔ STM32G474 连续运行、超时停车、断线/恢复、错误状态、周期统计。

#### 主线 B：Linux Camera / Audio

Camera 至少能讲：

- V4L2 open/ioctl/REQBUFS/QUERYBUF/MMAP/QBUF/DQBUF/STREAMON/OFF。
- V4L2、Argus、GStreamer 在 Jetson 上的边界与使用场景。
- YUYV / MJPEG / NV12 / RGB，CPU copy 与零拷贝概念。
- timeout、断连、重新打开、subscriber-aware lifecycle。
- Camera 内参、畸变、重投影误差、CameraInfo。

Audio 至少能讲：

- ALSA PCM、period、buffer、S16_LE、sample rate、xrun。
- capture / playback 资源竞争。
- TTS 播放期间为什么需要 ASR input gate / audio focus。

最终证据：FPS/延迟/掉帧、Audio xrun、长稳、断开恢复。

#### 主线 C：端侧离线语音 AI

链路：

```text
ALSA → KWS → VAD → ASR → Router → LLM → TTS → Playback
```

重点不是“模型多”，而是：

- 确定性命令为什么优先于 LLM。
- LLM 为什么不能直接操作 CAN、shell、任意 RPC。
- ASR/TTS/LLM 如何解耦。
- Jetson 8GB 下为什么选 2B 作为默认模型。
- llama.cpp CUDA runtime、模型量化、TTFT、tokens/s、RSS/GPU 内存。
- TTS 与 LLM 是否并行，如何降低首包延迟。
- TTS 播放时如何避免回声造成 ASR 误触发。

最终证据：ASR RTF、LLM TTFT/tok/s、TTS first-audio、RSS/GPU、端到端延迟、长稳。

#### 主线 D：ROS2/Nav2 与传感器系统集成

必须能讲：

- `map → odom → base_link → laser/camera` TF 语义。
- `LaserScan` 的 angle/range/time 字段。
- Nav2 costmap、planner、controller 的输入输出。
- scan stale 与 `/cmd_vel` stale 的安全语义。
- source timestamp、receive timestamp、publish timestamp 的区别。
- `message_filters` 只是消息匹配，不等于时间同步本身。

最终证据：真实/回放 LaserScan → costmap → planner/controller → `/cmd_vel` → safety adapter。

## 2. 当前技术基线与必须封板的内容

### 2.1 cockpit-system 分层继续保持

```text
Linux / Hardware
       ↓
cockpit/drivers
       ↓
cockpit/modules
       ↓
cockpit/library/driver
       ↓
Navigator / Agent / ROS2 Bridge
```

原则：

- `drivers`：只做 Linux / 硬件适配。
- `modules`：领域逻辑、算法、纯模型。
- `library/driver`：生命周期、IPC/gRPC、资源所有权。
- `agent`：语音、交互、conversation、tools、LLM。
- ROS2 Bridge：ROS 类型留在桥接边界，不污染纯 domain 模块。

### 2.2 Voice baseline 不再重构

当前已经有：

- Sherpa-ONNX
- KWS
- Silero VAD
- SenseVoiceSmall INT8
- Kokoro TTS
- llama.cpp + Qwen3.5-2B Q4_K_M
- deterministic allowlist router
- 语音状态机与安全边界

后续只做：Jetson 真机性能、input gate/audio focus、故障恢复和最终数据。

### 2.3 CAN V1 协议保持冻结

继续使用正式控制帧、heartbeat、fault、motion status、odom；不再为了“看起来企业化”频繁重构协议。

重点转移到：

- 真机 can0 ↔ STM32G474
- 200 ms command watchdog
- 300 ms heartbeat
- sequence/CRC
- bus-off/error recovery
- Nav2 safety adapter

### 2.4 scripts 重构立即结束

仅收掉当前两个剩余 P2：

1. Jetson ARM64 上 `COCKPIT_LLAMA_CPP_CUDA=OFF` 时，CUDA architectures 必须为空，保证 CPU fallback 可用。
2. llama runtime profile 变化后，安装 runtime `bin/` 前清理旧文件；build cache identity 包含 architecture，避免跨架构污染。

完成后脚本目录封板，不再继续组织结构重构。

## 3. 吸收外部机器人/语音项目的优点

参考资料中的优点只吸收机制，不复制平台实现。

### 3.1 值得吸收

| 外部项目优点                         | AIM2 对应实现                                      |
| ------------------------------------ | -------------------------------------------------- |
| V4L2 MMAP + timeout + 断线重连       | 强化 Jetson Camera driver 真实故障恢复             |
| 无订阅者时释放采集资源               | 对长期运行的 Camera lifecycle 做验证               |
| TF + LaserScan + 多传感器坐标统一    | ROS2/Hawkeye 使用统一 frame contract               |
| Camera/LiDAR 时间匹配                | 先统一 timestamp 语义，再做 ApproximateTime/同步   |
| TTS 与 LLM 异步/双缓冲               | 降低 first audio latency                           |
| TTS 期间暂停/抑制 ASR                | AIM2 用 interaction 层 input gate/audio focus 实现 |
| Tool 层与模型接口层分离              | Agent tool 保持 typed interface，不依赖具体模型    |
| 多步 Agent 的 step-output dependency | 后续可做受限 workflow，但不影响当前秋招主线        |
| 记忆数据临时文件 + 原子替换          | 未来长期 memory 可采用                             |
| `/proc` 资源监控、日志、自动恢复     | Jetson runtime health / benchmark / systemd        |
| 共享内存/低拷贝思路                  | 仅在 Camera 等高带宽链路 profiling 后采用          |

### 3.2 不直接照搬

外部项目中的 RK-MPP / RGA / RKNN、ROS1 move_base、STM32F103、UART、Ollama、Piper 等属于平台实现，不作为 AIM2 目标。

AIM2 对应：

```text
RK SoC / RKNN      → Jetson / CUDA / TensorRT（需要时）
ROS1 move_base     → ROS2 Nav2
UART               → CAN FD
STM32F103          → STM32G474
Ollama             → llama.cpp runtime
Piper              → Kokoro / Sherpa TTS
```

## 8. 阶段 4：ROS2/Nav2 软件闭环

### 8.1 软件阶段目标

```text

        ↓

        ↓
local/global costmap
        ↓
planner
        ↓
controller
        ↓
/cmd_vel
        ↓
Safety Adapter
        ↓
Fake Chassis Sink
```

### 8.2 必做测试

- 障碍 marking。
- 障碍 clearing。
- goal success。
- goal cancel。
- planner/controller restart。
- scan stale。
- `/cmd_vel` stale。
- linear/angular clamp。
- 非有限速度拒绝。
- watchdog 归零。

### 8.3 生产安全层

不能直接做：

```text
Nav2 /cmd_vel → CAN 0x101
```

必须经过独立的 bounded safety adapter：

```text
/cmd_vel
 ↓
finite check
 ↓
unit conversion
 ↓
linear / angular clamp
 ↓
slew/acceleration limit
 ↓
enable/authority
 ↓
watchdog / stale rejection
 ↓
CAN 0x101
```

最终与 STM32 自身 200 ms command watchdog 形成双层失效保护。

## 10. C1 真机 4 天冲刺

四天只做必须依赖实物的事情，不在现场做目录重构、框架设计、基础 launch 编写。

### Day 1：C1 bring-up + 数据特性

必须完成：

- `lsusb` / `dmesg` / `/dev/serial/by-id`。
- 确认 driver 版本/commit。
- `/scan` 可用。
- `ros2 topic hz/bw /scan`。
- 保存真实 `LaserScan` 字段。
- 确认 scan rate、scan_time、timestamp 单调性。
- 观察 NaN/Inf/out-of-range 行为。
- 开始录 rosbag。

数据场景至少：空旷、墙、墙角、走廊、动态人物/障碍、静止、移动。

### Day 2：真实安装 TF + 数据集

- 将 C1 固定到机器人。
- 实测 `base_link → laser` 的 x/y/z/roll/pitch/yaw。
- RViz 检查方向、左右镜像、90° 偏差。
- 保存正式配置。
- 录制含 TF 的真实 bag。
- 测试 USB 拔插、driver restart。

### Day 3：真实 Nav2 链路

```text
C1 → /scan → costmap → planner/controller → /cmd_vel → safety adapter
```

必须验证：

- 真实箱子进入 costmap。
- 移除后 clearing 正常。
- goal/cancel。
- scan stale 不允许继续盲走。
- safety adapter 限幅/归零。

如果底盘条件允许，再接：

```text
/cmd_vel → safety → CAN FD → STM32G474 → Motor
```

### Day 4：稳定性 + 故障注入 + 证据收集

优先做：

- 连续运行 1~2 h 或更长。
- driver restart 多轮。
- USB 热插拔多轮。
- Nav2 restart。
- scan 断流/恢复。
- 障碍突然出现/消失。
- CPU 有负载情况下观察 scan Hz/jitter。

雷达归还前必须备份：

- 所有 rosbag2。
- 驱动版本与依赖版本。
- YAML / launch / RViz config。
- udev/设备标识。
- TF 实测值。
- benchmark 输出。
- journal/故障日志。
- 实物安装照片、RViz 截图。

## 11. 时间同步：做到“语义正确”，不做过度研究

秋招前优先建立可信 timestamp contract：

```text
sensor sampling/source timestamp
        ↓
driver receive timestamp
        ↓
processing
        ↓
publish timestamp
```

必须明确：

- Camera frame timestamp 来源。
- C1 `header.stamp` 来源。
- 未来 IMU timestamp 来源。
- clock domain。
- timestamp regression 处理。
- stale threshold。

C1 真机期间测：

- `stamp[n] - stamp[n-1]`
- mean / P95 / max period
- jitter
- regression count

注意：ROS2 `message_filters`/ApproximateTime 解决的是“已有时间戳消息的匹配”，不是硬件时钟同步本身。

秋招前不强求 PTP/PPS/硬件触发，除非真实需求明确。

## 12. 多传感器融合：只做一条，且放在核心闭环之后

### 12.1 优先级

Camera-LiDAR 融合是 B 级加分项，不允许阻塞 Camera、CAN、Nav2、LLM 真机证据。

### 12.2 最小可展示方案

思岚 C1 是 2D LiDAR，适合做：

```text
LaserScan (r, θ)
 ↓
x = r cosθ
y = r sinθ
z = 0
 ↓
T_camera_lidar
 ↓
Pc = R Pl + t
 ↓
Camera intrinsics K
 ↓
u = fx X/Z + cx
v = fy Y/Z + cy
 ↓
投影到图像 / detection box
 ↓
估计目标距离
```

必须具备：

- Camera intrinsics。
- Camera ↔ LiDAR extrinsics。
- timestamp matching。
- frame convention 清晰。
- 异常点过滤。

由于 C1 是 2D 扫描平面，不把它包装成“3D 点云感知融合”。

## 13. 工程化与部署

### 13.1 systemd

秋招前至少让核心服务支持：

- `Restart=on-failure`
- journal stdout/stderr
- 明确用户/设备权限
- 音频/视频设备 ready 后再启动
- 合理的 dependency/ordering

避免通过固定 `sleep 10` 作为长期方案；最终优先使用真实依赖与 readiness。

### 13.2 Runtime health

至少监控：

- process RSS
- CPU
- GPU memory/load（AI）
- thread count
- Camera FPS / dropped frames
- Audio xrun
- scan rate/stale
- CAN error state

不需要秋招前造“大而全监控平台”，优先有可复用 benchmark/diagnostic 输出。

## 21. 最终原则

AIM2 秋招阶段只遵守三条：

> **第一，现有广度已经够，后续以深度为主。**  
> **第二，软件能提前做完的全部提前做；稀缺硬件时间只用于真机验证和数据采集。**  
> **第三，所有简历亮点最终都要落到“设计 + 故障 + 测试 + 指标 + 真机证据”。**

这套计划的终点不是做成一个功能最多的机器人，而是形成一套能够证明嵌入式 Linux、机器人系统集成、实时通信和端侧 AI 工程能力的秋招项目。
