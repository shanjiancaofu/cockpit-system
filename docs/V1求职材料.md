# Cockpit System V1 求职材料包

## 简历一行版

在Jetson Orin Nano 8GB上实现多进程智能座舱：V4L2 RAW10 Software ISP、ALSA语音链、
SenseVoice/Qwen3.5-2B/Kokoro本地AI、Qt/QML UI及ROS2/Nav2桥接；完成延迟/资源 profiling、
进程故障恢复、Sanitizer CI和20分钟整机验证。

## 简历项目版

- 设计`systemd → Navigator → module child`多进程架构，以版本化C ABI、gRPC、本地socket和
  POSIX shared memory隔离Camera、Audio、Agent、Vehicle、HMI等资源所有权与故障边界。
- 实现IMX219 V4L2 MMAP RAW10采集和CPU Software ISP，采用采集/ISP双线程有界队列、NEON unpack、
  BLC/WB/demosaic/gamma；720p30实测P95 5.61ms、CPU 46%、0 drop/gap，1080p30 P95 11.22ms。
- 集成Sherpa KWS、Silero VAD、SenseVoice ASR、Qwen3.5-2B llama.cpp和Kokoro TTS；白名单动作与
  LLM文本路径分离，LLM不能直接执行shell、RPC或CAN。
- 实现Camera generation隔离、first-output deadline和100→5000ms指数退避；覆盖旧帧假恢复、
  ISP late/failure、二次独立故障和bounded stop行为测试。
- 实现Navigator startup/restart/health snapshot和managed llama-server父进程死亡约束；真实kill后
  Agent/UI保持存活，LLM约5.2s恢复，Camera模块可重启。
- 建立Debug/Release、ASan/UBSan、TSan和ROS2/Nav2 CI；UI、Camera、Audio、Voice、LLM、ROS2并发
  运行并记录RSS、CPU、温度、FPS、drop和故障恢复证据。

## 三分钟讲解

这个项目不是单独的语音Demo，而是运行在Jetson 8GB上的完整车端多媒体和本地AI系统。最底层是
V4L2、ALSA和SocketCAN驱动；Camera、Audio、Vehicle等领域能力放在独立module process中，由
Navigator统一启动、监控和限次重启。UI、Agent和ROS2通过typed gRPC、共享内存和本地socket访问，
避免多个进程同时拥有同一个硬件资源。

Camera有Argus hardware ISP、UVC和Software ISP三条严格组合的pipeline。Software ISP从RAW10 MMAP
采集开始，经过有界队列和CPU ISP输出BGRx共享帧。720p30的P95约5.6ms、CPU约46%，1080p30的P95
约11.2ms、CPU约91%，因此720p是V1默认性能模式，1080p是质量模式，8MP CPU约246%不作为实时模式。

语音链是KWS、VAD、ASR、Agent、LLM和TTS。确定性白名单命令可以打开Camera等受控功能；普通问题
才进入Qwen；LLM输出永远只是文本，不能直接shell、RPC或CAN。模型进程由Agent托管，父进程死亡时
自动退出，异常后有bounded timeout和重启。

最后我不是只跑module tests，而是把UI、Camera、Audio、Voice、LLM和ROS2一起运行，记录资源、温度、
FPS和恢复行为。一次audio_driver SIGSEGV被完整保留为残余风险，后续Target/ASan/TSan未复现，因此
没有伪造“已修复”结论。这体现了项目对证据边界和工程风险的处理。

## 十分钟技术展开

1. 解释为什么systemd只管理Navigator，而不是十几个独立service。
2. 展开module ABI、子进程、restart limit、health snapshot和orphan process约束。
3. 对比gRPC、shared memory和local socket分别承载控制、视频帧和PCM的原因。
4. 展开V4L2 MMAP ownership、DQBUF/QBUF、RAW10 unpack和bounded queue backpressure。
5. 用720p/1080p/8MP数据解释CPU ISP的产品取舍，而不是只展示“能跑”。
6. 讲Camera recovery generation、first processed frame和重复backoff reset。
7. 展开KWS模型兼容问题：为什么C++ CLI通过但public C API路径失败，以及为何固定旧官方模型。
8. 讲Agent白名单、LLM文本边界、timeout、follow-up window和TTS playback receipt。
9. 展开Qt人工验收与offscreen QML test的差异。
10. 展开full-system资源曲线、软件故障注入和accepted residual risk决策。

## 高频面试问答

### 为什么CameraFrame不用gRPC直接传整帧？

控制和状态适合typed RPC，但720p/1080p连续图像若反复序列化和复制，会增加CPU、内存带宽和延迟。
项目用POSIX shared memory双缓冲传帧，用gRPC传生命周期、状态和控制，职责更清晰。

### 为什么有界队列容量很小？

预览更重视最新帧而不是完整历史。消费者跟不上时继续堆积只会扩大延迟和内存，所以队列容量固定，
允许丢弃过时帧并显式统计drop和sequence gap。

### Camera reopen成功为什么不能立即标Running？

设备open成功不代表已经产生可用输出。必须看到当前generation的新RAW帧完成ISP并仍在first-output
deadline内，才能避免旧backend残留帧造成假恢复。

### 为什么2B模型比4B更适合8GB Jetson？

系统必须与Camera buffer、ASR、TTS、ROS2和UI并发。模型选择看的是全系统内存、swap、TTFT和热状态，
不是单独LLM的效果。2B为其他实时模块保留了更可控的资源余量。

### 为什么LLM不能直接生成函数调用控制车辆？

自然语言模型输出不具备确定性安全语义。项目只允许固定白名单router生成typed action；未知请求进入
LLM后只能返回用户可见文本，不能越过Agent直接访问shell、RPC或CAN。

### 如何处理一次无法复现的SIGSEGV？

保留原始时间、退出信号、恢复行为和缺失core的限制；增加针对性生命周期压力、Target重复运行、
ASan和TSan。若仍不复现，可以按明确残余风险冻结，但不能写成“根因已修复”。

### Full-system test为什么比模块测试重要？

Jetson 8GB的主要风险是模型、Camera、UI和ROS2同时运行后的资源竞争、timeout和进程生命周期。
模块测试证明局部行为，整机测试才能验证容量、热状态、恢复和最终用户界面。
