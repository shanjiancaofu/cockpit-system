# 配置说明

开发配置是 `configs/development.yaml`，发布包模板是 `configs/production.yaml`，二者都由
`cockpit/core/config/SystemConfig` 在进程启动时解析和校验。Navigator 与所有 module child 共用
同一个业务配置入口。

## Navigator

```bash
_output/build/x86_64-debug/bin/cockpit-navigator \
  --config configs/development.yaml \
  --module-dir _output/build/x86_64-debug/lib/cockpit/modules \
  --socket /tmp/cockpit-navigator.sock \
  --mode normal
```

- 模块名、动态库名、启动顺序和 mode 组合由 `cockpit/navigator/run_config/run_config.cc` 维护，属于
  产品运行策略，不通过 YAML 暴露。
- `--config` 是统一业务配置；module child 不读取单独的 Navigator 配置。
- `--module-dir` 只指定安装后的动态库目录，默认根据 Navigator 可执行文件位置推导。
- `--socket` 指定本地控制 Socket；`--mode` 可选 `normal`、`development`、`cloud` 或 `upgrade`。
- 模块必须在启动超时内完成动态库加载、ABI 校验和 `start`，否则不会进入 running。
- 时间窗口内连续崩溃超过上限后模块进入 failed，避免无限重启。

运行时控制：

```bash
cockpit-ctl runtime status --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime switch development --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime restart camera_driver --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime reload --socket /tmp/cockpit-navigator.sock
```

控制面支持 `status`、`mode`、`switch`、`start`、`stop`、`restart`、`reload` 和 `shutdown`。
`reload` 会按当前 mode 停止并重新加载全部模块，主要用于升级回滚。`upgrade` 是 safe-ota 使用的独占
模式，不作为日常业务组合。预留模块未实现前不进入 mode，显式启动也会返回失败。
Runtime Socket 的 `status/mode` 查询上限为 1 秒；`cockpit-ctl` 的 switch/start/stop/restart/reload
有序变更等待上限为 15 秒。safe-ota 的同步 mode 切换上限单独固定为 30 秒。这些边界不通过 YAML
调整。

## 基础信息

```yaml
system:
  name: cockpit-system
  vehicle_id: car_001

paths:
  data_dir: _output/runtime/data
  log_dir: _output/runtime/logs
  run_dir: _output/runtime/run
```

- `system.name`：系统名称。
- `system.vehicle_id`：车辆标识，未来用于云端 topic、存储和诊断。
- `paths.data_dir`：运行数据目录。
- `paths.log_dir`：日志目录。
- `paths.run_dir`：本地 socket 等短生命周期运行文件目录。

车端直接使用以上配置，相对路径由 `/cockpit-system` 工作目录解析。WSL 构建和运行脚本会设置
`COCKPIT_RUNTIME_DIR=$PWD/_output/runtime`，集中覆盖为：

```text
_output/runtime/data
_output/runtime/logs
_output/runtime/logs/topics
_output/runtime/run
```

该环境变量只改变开发机运行输出，不写回业务 YAML，也不改变发布包中的车端目录语义。手动执行
构建产物时可先导出同名变量；未设置时严格使用 YAML 中的路径。

开发配置中的 `tools.topic.dir` 默认是 `_output/runtime/logs/topics`，同样会随
`COCKPIT_RUNTIME_DIR` 覆盖；因此直接运行 topic file backend 也不会在仓库根目录创建 `logs/`。

## 日志

```yaml
logging:
  level: info
  dump_time_secs: 5
  cut_off_time_mins: 5
  max_files: 10
  mirror_stderr: true
```

- `level`：`debug/info/warn/error`。
- `dump_time_secs`：内存日志缓冲刷入当前文件的周期，范围 1–60 秒。
- `cut_off_time_mins`：有日志写入时切换新文件的周期，范围 1–1440 分钟；空闲模块不会持续创建空文件。
- `max_files`：每个模块最多保留的日志文件数量，范围 1–100，超过后删除最旧文件。
- `mirror_stderr`：是否同时输出到终端。

日志文件按 `<模块>_YYYYMMDD_HHMMSS_mmm_序号.log` 命名。当前默认每 5 分钟切分、每个模块最多
保留 10 个文件；日志不再按单文件字节数提前切分。

## 服务地址

| gRPC 接口 | 所属模块 | 默认地址 | 用途 |
|---|---|---|---|
| vehicle-data | `vehicle_driver` | `127.0.0.1:50050` | VehicleState streaming |
| gateway | `transfer` | `127.0.0.1:50051` | UI、topic 和车辆状态查询 |
| audio | `audio_driver` | `127.0.0.1:50052` | PCM 采集状态、设备指标和 `PlayPcm` |
| voice interaction | `agent` | `127.0.0.1:50053` | 语音交互控制和回复 |
| camera | `camera_driver` | `127.0.0.1:50054` | 相机 list/start/stop/status/photo |
| recording | `recording` | `127.0.0.1:50055` | 研发录包、时间线和完整性诊断 |
| media | `media` | `127.0.0.1:50056` | 固定 track ID 列表、播放状态和控制 |
| sentinel | `sentinel` | `127.0.0.1:50057` | 哨兵 Arm/Disarm、状态和取证结果 |
| bridge | `bridge` | `127.0.0.1:50058` | typed goal/cancel/map pose 和 bridge 状态 |

`retry_delay_ms` 控制断线重试基础间隔，`stream_timeout_ms` 控制 streaming RPC 的会话超时。
上表是便于开发机调试的 TCP 默认值。发布模板使用
`unix:/cockpit-system/run/<service>.grpc.sock`，配合 systemd 的 `UMask=0077` 把本地控制面限制在
同一服务身份内；如需让运维用户直接调用 CLI，应通过受控用户组和 socket 权限开放，不应改回对所有
本机进程可访问的 TCP 端口。

## 哨兵模式

```yaml
services:
  sentinel:
    auto_arm: false
    vehicle_data_address: 127.0.0.1:50050
    cooldown_ms: 30000
    max_event_age_ms: 5000
    queue_capacity: 64
    rpc_timeout_ms: 1000
    grpc:
      listen_address: 127.0.0.1:50057
```

`auto_arm` 默认关闭，避免服务重启后未经用户确认自动布防。Sentinel 只订阅 Vehicle Driver 解码后的
typed `ChassisEvent`；`queue_capacity`、事件年龄、冷却和 Camera/Recording RPC 都有上限。生产使用
`unix:/cockpit-system/run/sentinel.grpc.sock`。配置不包含 CAN ID 或字节位置；这些字段必须等 STM32
协议联调后进入专用 codec/协议文档，不能写成未经确认的默认值。

## Bridge

```yaml
services:
  bridge:
    provider: fake
    fake_outcome: succeeded
    nav2_action_name: /navigate_to_pose
    nav2_server_timeout_ms: 1000
    goal_timeout_ms: 30000
    grpc:
      listen_address: 127.0.0.1:50058
```

允许的 provider 是 `disabled|fake|ros2_nav2`。fake outcome 只有 `succeeded|rejected|failed|stalled|disconnected`；
其中 stalled 用于验证有界 goal timeout，disconnected 用于验证明确失败和恢复到 idle。生产默认
`disabled`，地址为 `unix:/cockpit-system/run/bridge.grpc.sock`。`ros2_nav2` 仅在显式 ROS2 构建中可用，
`nav2_action_name` 必须是绝对 ROS action 名；action server 发现和 goal/cancel acknowledgement 使用
不超过 5 秒的 `nav2_server_timeout_ms`，整个任务仍由 `goal_timeout_ms` 有界控制。

ROS2 provider 是可选构建，不影响默认 Ubuntu 构建：

```bash
cmake -S . -B _output/build/ros2 -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCOCKPIT_ENABLE_ROS2=ON
```

先运行 `bash scripts/setup-ros2-humble-nav2.sh` 安装并核验 pinned Ubuntu 22.04 amd64 deb。启用后需要
`ament_cmake`、`rclcpp`、`rclcpp_action`、`nav2_msgs`、`sensor_msgs` 和 `geometry_msgs`。当前 VM 已用
fake Nav2 action server 验证 provider 合同，但未验证真实地图、localization 或机器人底盘。

## 音频

```yaml
hardware:
  audio:
    input_device: default
    output_device: default
    sample_rate_hz: 16000
    channels: 1
    frame_ms: 20
```

当前采集和播放实现均使用 ALSA。`sample_rate_hz: 16000`、`channels: 1` 和 `frame_ms: 20` 定义的是
麦克风采集帧以及 KWS/VAD/ASR 的输入合同；配置加载会拒绝其他值，避免采集格式与固定帧模型不一致。
播放不复用该采集采样率：Audio gRPC 接受 16 kHz mono 固定提示音和 24 kHz mono Kokoro 原生输出，
再由配置的 ALSA `output_device` 适配物理设备。Jetson 部署时应将 `input_device` 和 `output_device`
改为实际设备，例如 `plughw:1,0`，并单独核验物理端采样率和声道数。

当前 Ubuntu USB PCM2902 实测物理能力为 S16_LE、采集 mono、播放 stereo，采样率只支持 44.1/48 kHz。
使用 `plughw:CARD=Device,DEV=0` 时，16 kHz 采集请求在 USB 端以 48 kHz 运行后转换给语音模型，
16 kHz 提示音和 24 kHz Kokoro 输出也都在 USB 播放端转换为 48 kHz。16 kHz 是算法合同，不是该声卡
的物理采样率。

语音前端属于 Agent，不属于 Audio Driver：

```yaml
features:
  voice:
    enabled: false
    kws:
      enabled: false
      provider: mock
      cooldown_ms: 1500
      wake_word: 你好小山
      model_dir: ""
    vad:
      provider: mock
    speech_segment:
      pre_roll_ms: 100
      max_segment_ms: 15000
    asr:
      provider: mock
```

- 当前基础仓库的 `vad.provider` 支持 `disabled`、`mock` 或 `sherpa`；`asr.provider` 支持 `mock`
  或 `sherpa-sensevoice`。默认 CI 仍只使用 `mock`。
- 主仓库不再提供 Energy VAD；RMS、峰值和削波只用于音频诊断。
- `pre_roll_ms` 保留起始语音前的少量音频。
- 启用语音时不能把 VAD 设为 `disabled`。
- Audio Driver 只采集、发布和播放 PCM；VAD、分段、ASR 和 TTS 都在 `agent/`。

## 相机

```yaml
services:
  camera:
    capture_backend: gstreamer
    preview_stale_timeout_ms: 2000
    synthetic_fault: none
    synthetic_fault_after_frames: 30
    shared_memory_name: /cockpit_camera_preview
    max_frame_bytes: 8388608
    photo_directory: photos
    photo_jpeg_quality: 90
    photo_max_frame_age_ms: 2000
```

帧像素通过 POSIX shared memory 传输，gRPC 只负责控制和状态。`max_frame_bytes` 必须覆盖目标
分辨率和像素格式的单帧大小。

- `capture_backend` 支持 `gstreamer` 和开发测试用 `synthetic`；合成设备路径固定为
  `synthetic://camera0`。
- GStreamer 后端的 USB 摄像头使用 `/dev/video*`，Jetson CSI 使用 `nvargus://<sensor-id>`；
  CSI 管线由 `nvarguscamerasrc`、NVMM 和 `nvvidconv` 转为共享内存需要的 RGB/BGRx 帧。
- `preview_stale_timeout_ms` 同时用于“启动后始终无帧”和“已有帧后卡住”的运行期判定。
- `synthetic_fault` 支持 `none`、`no_frames`、`stall`、`disconnect`；后两者在
  `synthetic_fault_after_frames` 后触发。
- 相对 `photo_directory` 以 `paths.data_dir` 为基准，默认保存到 `data/photos`。
- `photo_jpeg_quality` 范围为 1-100。
- 拍照只接受不超过 `photo_max_frame_age_ms` 的最新帧，避免保存卡住的旧画面。
- `camera_driver` 内部通过 MessageBus 发布 `/camera/status` 和 `/camera/frame_meta`，录包桥只转发
  轻量元数据，不传输帧像素。

## 本地媒体

```yaml
services:
  media:
    provider: disabled
    manifest: _output/media/manifest.yaml
    sink: fakesink
    grpc:
      listen_address: 127.0.0.1:50056
```

- `provider` 支持 `disabled`、`mock`、`gstreamer-fakesink` 和 `gstreamer`；开发和生产默认均为
  `disabled`。
- `disabled` 仍启动有界 gRPC 控制面并报告 health=DISABLED，但没有曲目且所有播放命令明确失败。
- `mock` 只提供两个固定 track ID，用于 play/pause/resume/next/stop 自动化，不播放真实声音。
- `gstreamer-fakesink` 和 `gstreamer` 从 `manifest` 加载固定曲目；manifest 路径相对 manifest 文件所在
  目录，曲目可以位于其受控子目录中的普通非 symlink 文件，并且必须通过锁定的 SHA-256 校验。
- development 配置使用 `_output/media/manifest.yaml`；production 配置使用
  `/cockpit-system/media/manifest.yaml`。媒体资源不放进源码，也不默认打进 OTA 软件包。
- `gstreamer-fakesink` 使用 GStreamer `playbin3` + `fakesink` 做状态/EOS 前的控制面验证；`gstreamer`
  要求 `sink: alsasink`，真实扬声器输出和音频焦点仍需单独验收。
- media module 只进入显式 `ui` mode，不增加独立 systemd service；HMI `play_music` 在真实播放
  owner 和音频焦点策略完成前仍保持显式失败。

Manifest 最小格式：

```yaml
tracks:
  - id: cabin_music_01
    title: Cabin Music
    artist: Cockpit
    duration_ms: 180000
    path: cabin_music_01.wav
    sha256: <64 lowercase hexadecimal characters>
```

## 研发录包

```yaml
services:
  recording:
    auto_start: false
    directory: recordings
    vehicle_data_address: 127.0.0.1:50050
    stream_timeout_ms: 10000
    retry_delay_ms: 200
    max_sessions: 100
    max_total_bytes: 5368709120
    max_session_bytes: 1073741824
    max_session_duration_seconds: 14400
    min_free_bytes: 536870912
    grpc:
      listen_address: 127.0.0.1:50055
```

- 相对 `directory` 以 `paths.data_dir` 为基准，默认写入 `data/recordings/sessions`。
- `auto_start` 适合固定诊断任务；日常开发建议通过 `recording-ctl` 显式控制。
- 完成会话包含 `manifest.json`、`vehicle_state.jsonl`、`events.jsonl`、`data_files.jsonl`
  和 `COMPLETE`。
- `manifest.json` 记录 project、schema_version、vehicle_id、config_path、config_checksum、
  git_commit、build_type、binary_version 和 sources，便于研发复盘。
- `recording-ctl --detail <session-id>` 可查看单个会话的 manifest 摘要和复盘元数据。
- `events.jsonl` 只接受合法 JSON value，并对 topic、manifest 和文件索引中的字符串统一转义。
- `data_files.jsonl` 只索引相机、音频、语音等大块数据文件的路径、source、kind、size 和
  checksum；`copy_into_session` 请求会把源文件复制到会话 `artifacts/`、记录相对路径并在未提供
  checksum 时自动生成 `fnv1a64`。
- `recording-ctl --verify <session-id>` 校验索引格式、路径边界、文件类型、大小和 checksum；当前
  支持 `fnv1a64`，空值和其他算法显示为 unavailable。
- `recording-ctl --report <session-id> --timeline-limit 100 --issue-limit 100 --output json`
  汇总 manifest、时间线、损坏行和 artifact 完整性；两类 limit 范围均为 1-1000，报告不健康时
  返回退出码 3。
- `recording-ctl --verify-all --from-started-ms 0 --to-started-ms 0 --limit 100 --output json`
  批量汇总会话完整性；时间范围包含端点，结束时间 0 表示不限制，limit 范围为 1-1000。存在
  damaged 或 unavailable 会话时返回退出码 3，单个会话失败不会中断整批。
- 异常退出遗留的 `.recording_*` 会在下次启动时改名为 `interrupted_*` 并写入
  `INTERRUPTED` 标记。
- 未启动录制时，`AppendEvent` 和 `AppendDataFile` 返回前置条件错误，不会伪装成成功。
- 当前已记录 VehicleState，并通过 `AppendEvent` 接收通用事件；camera 拍照文件会复制进当前会话，
  voice response 可写入 `events.jsonl`；camera status/frame metadata 通过 `camera_driver` 内部
  MessageBus 桥接到 recording 模块。音频大块数据源尚未接入。
- `max_sessions` 和 `max_total_bytes` 同时生效；完成会话后自动从最旧数据开始清理。
- 活动会话每次写入前同时检查 `max_session_bytes`、`max_session_duration_seconds`、
  `max_total_bytes` 和 `min_free_bytes`，超限后进入可诊断 fault 状态。
- 复制到录制会话的数据文件只能来自 `paths.data_dir`，不接受目录外路径或符号链接。
- `recording-ctl --prune` 按同一策略立即执行清理，不会删除当前活动会话。

## Navigator 运行策略

活动 YAML 不包含模块清单和依赖表。模块名、启动顺序、强弱依赖和 mode 组合的唯一来源是
`cockpit/navigator/run_config/run_config.cc`。旧 `runtime.dependencies` 及只展示它的
`cockpit-ctl dependencies` 已删除，避免业务配置和实际 Runtime 各维护一份策略。

## 语音和 AI

```yaml
features:
  voice:
    enabled: false
    vad:
      provider: mock
    speech_segment:
      pre_roll_ms: 100
      max_segment_ms: 15000
    asr:
      provider: mock
  ai:
    asr_timeout_ms: 3000
    assistant_timeout_ms: 10000
    command_execution_timeout_ms: 3000
    tts_synthesis_timeout_ms: 5000
    follow_up_window_ms: 8000
```

基础仓库只提供可测试的 mock 实现，不提供算法动态插件 ABI。KWS 已有项目内稳定接口和
`VoiceInputGate`，但真实 Sherpa runtime/model 只属于显式 Agent 产品构建；它们不进入主项目依赖，
也不由 Audio Driver 加载。

`features.voice.kws` 控制唤醒入口：

- `enabled=false`：保持旧行为，所有 PCM 继续进入 `SpeechPipeline`，便于开发和自动化测试。
- `enabled=true`：`Idle` 状态下 PCM 只送入 KWS；`Listening`/`FollowUp` 状态下 PCM 送入
  `SpeechPipeline`；`Waking`、`Recognizing`、`Routing`、`Executing`、`Thinking`、`Speaking`、
  `Cancelled`、`ErrorRecovery` 和 `ShuttingDown` 暂停输入处理。
- `provider=mock` 可在普通 CI 中验证 gate/cooldown；`provider=sherpa` 需要
  `COCKPIT_ENABLE_SHERPA_AGENT=ON` 的产品构建，并且必须通过 `keywords_file` 传入已 tokenized 的
  唤醒词文件。
- `cooldown_ms` 使用 `steady_clock`，防止连续重复唤醒。
- `wake_word` 仅供 `provider=mock` 使用；`provider=sherpa` 时必须为空。
- `keywords_file` 仅供 `provider=sherpa` 使用，指向 tokenized keywords 文件。
- `model_dir` 是 Sherpa KWS 模型目录，只有启用 `provider=sherpa` 时要求非空。
- 产品机路径固定在 `/cockpit-system/ai`，例如
  `keywords_file=/cockpit-system/ai/config/kws-keywords.txt`、
  `model_dir=/cockpit-system/ai/models/kws/sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`。

AI deadline 字段均为正整数毫秒，分别由 `SpeechPipeline`、`VoiceInteractionService` 的 Assistant 调用、
ActionDispatcher 及 `AudioPlaybackClient` 的 TTS synthesis 消费。业务 deadline 统一来自
`steady_clock`；Gateway/HMI 等 gRPC client 只把剩余预算换算到 `system_clock` deadline，并支持
`TryCancel`。TTS synthesis 预算不包含 PCM 在扬声器上的实际播放时间。
`follow_up_window_ms` 是真实语音播放完成后保持 `FOLLOW_UP` 的 monotonic 时间窗口；窗口内的新
transcript 直接进入下一轮识别，超时、打断或停机都会使该窗口失效。

旧 `request_timeout_ms` 已删除，写入活动 YAML 会按未知字段拒绝启动。`wait_for_speech_ms`、
`llm_first_token_ms`、`llm_total_ms` 和 `tts_first_audio_ms` 尚无真实 consumer，继续只保留在规划文档，
不进入活动配置。

## 未来配置契约

以下能力保留在规划中，但当前没有真实 consumer，因此字段名不进入活动 YAML，写入后会被严格
配置校验拒绝：

- WebSocket：候选职责是 gateway 的外部连接地址；实现 listener、鉴权和连接生命周期后再确定
  `services.gateway.websocket` 的最终结构。
- 云端上传：候选职责包括开关、broker、topic、QoS、设备身份、TLS、发布确认和重试；后端合同明确且
  `carupload` 建立真实 transport 后再确定 `services.cloud_uplink` 的最终结构。
- TTS 与交互模式：出现第二个真实 TTS 实现或 push-to-talk 等交互模式后，再引入
  `features.voice.tts_provider` 或 `features.voice.mode`。wake-word 第一阶段已经由
  `features.voice.kws.enabled` 控制，不再另设 mode 字段。
- LLM：真实 Assistant provider 接入并具备 deadline、取消和错误语义后，再引入
  `features.ai.provider` 与 `features.ai.model`。

`hardware.audio.capture_backend`、`hardware.audio.playback_backend` 和
`services.camera.frame_transport` 也不作为当前配置。现阶段采集、播放和相机帧传输分别固定为
ALSA、ALSA 和 POSIX shared memory。当前 VAD/ASR 通过 Agent 内的普通 C++ 接口注入 mock 实现，
不提供算法动态插件 backend。

## 配置原则

- 配置文件描述部署差异，不存放业务状态。
- 密钥和 token 不提交到仓库，未来使用环境变量或独立 secret 文件。
- 新增配置必须同步类型化结构、校验、示例和测试。
- 未知字段会携带完整 YAML 路径拒绝启动，避免拼错字段后静默使用默认值。
- 不允许模块自行重复解析 YAML。
