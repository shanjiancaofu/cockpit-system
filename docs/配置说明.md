# 配置说明

业务配置文件是 `configs/config.yaml`，由 `cockpit/core/config/SystemConfig` 在进程启动时解析和校验。
Navigator 与所有 module child 共用这一个业务配置入口。

## Navigator

```bash
_output/build/x86_64-debug/bin/cockpit-navigator \
  --config configs/config.yaml \
  --module-dir _output/build/x86_64-debug/lib/cockpit/modules \
  --socket /tmp/cockpit-navigator.sock \
  --mode normal
```

- 模块名、动态库名、启动顺序和 mode 组合由 `cockpit/navigator/run_config/run_config.cc` 维护，属于
  产品运行策略，不通过 YAML 暴露。
- `--config` 是统一业务配置；module child 不读取单独的 Navigator 配置。
- `--module-dir` 只指定安装后的动态库目录，默认根据 Navigator 可执行文件位置推导。
- `--socket` 指定本地控制 Socket；`--mode` 可选 `normal`、`development`、`cloud` 或 `upgrade`。
- 模块必须在启动超时内完成动态库加载、ABI 校验和 `start`，否则不会进入 running。
- 时间窗口内连续崩溃超过上限后模块进入 failed，避免无限重启。

运行时控制：

```bash
cockpit-ctl runtime status --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime switch development --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime restart camera_driver --socket /tmp/cockpit-navigator.sock
cockpit-ctl runtime reload --socket /tmp/cockpit-navigator.sock
```

控制面支持 `status`、`mode`、`switch`、`start`、`stop`、`restart`、`reload` 和 `shutdown`。
`reload` 会按当前 mode 停止并重新加载全部模块，主要用于升级回滚。`upgrade` 是 safe-ota 使用的独占
模式，不作为日常业务组合。预留模块未实现前不进入 mode，显式启动也会返回失败。
Runtime Socket 的客户端连接/读写和服务端回复上限均为 1 秒，当前不通过 YAML 调整。
safe-ota 的同步 mode 切换需要等待模块有序停止和启动，响应上限单独固定为 30 秒；连接和写入仍为
1 秒。

## 基础信息

```yaml
system:
  name: cockpit-system
  vehicle_id: car_001

paths:
  data_dir: data
  log_dir: logs
  run_dir: run
```

- `system.name`：系统名称。
- `system.vehicle_id`：车辆标识，未来用于云端 topic、存储和诊断。
- `paths.data_dir`：运行数据目录。
- `paths.log_dir`：日志目录。
- `paths.run_dir`：本地 socket 等短生命周期运行文件目录。

车端直接使用以上配置，相对路径由 `/cockpit-system` 工作目录解析。WSL 构建和运行脚本会设置
`COCKPIT_RUNTIME_DIR=$PWD/_output/runtime`，集中覆盖为：

```text
_output/runtime/data
_output/runtime/logs
_output/runtime/logs/topics
_output/runtime/run
```

该环境变量只改变开发机运行输出，不写回业务 YAML，也不改变发布包中的车端目录语义。手动执行
构建产物时可先导出同名变量；未设置时严格使用 YAML 中的路径。

## 日志

```yaml
logging:
  level: info
  dump_time_secs: 5
  cut_off_time_mins: 5
  max_files: 10
  mirror_stderr: true
```

- `level`：`debug/info/warn/error`。
- `dump_time_secs`：内存日志缓冲刷入当前文件的周期，范围 1–60 秒。
- `cut_off_time_mins`：有日志写入时切换新文件的周期，范围 1–1440 分钟；空闲模块不会持续创建空文件。
- `max_files`：每个模块最多保留的日志文件数量，范围 1–100，超过后删除最旧文件。
- `mirror_stderr`：是否同时输出到终端。

日志文件按 `<模块>_YYYYMMDD_HHMMSS_mmm_序号.log` 命名。当前默认每 5 分钟切分、每个模块最多
保留 10 个文件；日志不再按单文件字节数提前切分。

## 服务地址

| gRPC 接口 | 所属模块 | 默认地址 | 用途 |
|---|---|---|---|
| vehicle-data | `vehicle_driver` | `127.0.0.1:50050` | VehicleState streaming |
| gateway | `transfer` | `127.0.0.1:50051` | UI、topic 和车辆状态查询 |
| audio | `audio_driver` | `127.0.0.1:50052` | 音频控制、transcript、Speak |
| voice interaction | `agent` | `127.0.0.1:50053` | 语音交互控制和回复 |
| camera | `camera_driver` | `127.0.0.1:50054` | 相机 list/start/stop/status/photo |
| recording | `recording` | `127.0.0.1:50055` | 研发录包、时间线和完整性诊断 |

`retry_delay_ms` 控制断线重试基础间隔，`stream_timeout_ms` 控制 streaming RPC 的会话超时。

## 车辆数据

```yaml
services:
  vehicle_data:
    source: mock
    publish_interval_ms: 200

hardware:
  can:
    interface: vcan0
    simulator_backend: stdout
    simulator_interval_ms: 100
    receive_timeout_ms: 500
    max_idle_timeouts: 10
```

- `source`：`mock` 或 `socketcan`。
- `interface`：SocketCAN 接口，例如 `vcan0`、`can0`。
- `simulator_backend`：`stdout` 或 `socketcan`。

## 音频

```yaml
hardware:
  audio:
    input_device: default
    output_device: default
    sample_rate_hz: 16000
    channels: 1
    frame_ms: 20
```

当前采集和播放实现固定为 ALSA，语音链路固定使用 16 kHz、mono、PCM16、20 ms frame。
Jetson 部署时将 `input_device` 和
`output_device` 改为实际 ALSA device，例如 `plughw:1,0`。配置加载会拒绝其他采样率、声道数
或 frame 时长，避免配置值与固定帧模型不一致。

VAD：

```yaml
services:
  audio:
    auto_start: false
    vad:
      enabled: true
      speech_threshold_dbfs: -40.0
      speech_start_frames: 3
      speech_end_frames: 10
    speech_segment:
      pre_roll_ms: 100
      max_segment_ms: 15000
```

- `speech_threshold_dbfs` 必须根据真实麦克风环境标定。
- `speech_start_frames` 防止短噪声触发。
- `speech_end_frames` 提供尾部静音 hangover。
- `pre_roll_ms` 保留起始语音前的少量音频。

## 相机

```yaml
services:
  camera:
    capture_backend: gstreamer
    preview_stale_timeout_ms: 2000
    synthetic_fault: none
    synthetic_fault_after_frames: 30
    shared_memory_name: /cockpit_camera_preview
    max_frame_bytes: 8388608
    photo_directory: photos
    photo_jpeg_quality: 90
    photo_max_frame_age_ms: 2000
```

帧像素通过 POSIX shared memory 传输，gRPC 只负责控制和状态。`max_frame_bytes` 必须覆盖目标
分辨率和像素格式的单帧大小。

- `capture_backend` 支持 `gstreamer` 和开发测试用 `synthetic`；合成设备路径固定为
  `synthetic://camera0`。
- GStreamer 后端的 USB 摄像头使用 `/dev/video*`，Jetson CSI 使用 `nvargus://<sensor-id>`；
  CSI 管线由 `nvarguscamerasrc`、NVMM 和 `nvvidconv` 转为共享内存需要的 RGB/BGRx 帧。
- `preview_stale_timeout_ms` 同时用于“启动后始终无帧”和“已有帧后卡住”的运行期判定。
- `synthetic_fault` 支持 `none`、`no_frames`、`stall`、`disconnect`；后两者在
  `synthetic_fault_after_frames` 后触发。
- 相对 `photo_directory` 以 `paths.data_dir` 为基准，默认保存到 `data/photos`。
- `photo_jpeg_quality` 范围为 1-100。
- 拍照只接受不超过 `photo_max_frame_age_ms` 的最新帧，避免保存卡住的旧画面。
- `camera_driver` 内部通过 MessageBus 发布 `/camera/status` 和 `/camera/frame_meta`，录包桥只转发
  轻量元数据，不传输帧像素。

## 研发录包

```yaml
services:
  recording:
    auto_start: false
    directory: recordings
    vehicle_data_address: 127.0.0.1:50050
    stream_timeout_ms: 10000
    retry_delay_ms: 200
    max_sessions: 100
    max_total_bytes: 5368709120
    grpc:
      listen_address: 127.0.0.1:50055
```

- 相对 `directory` 以 `paths.data_dir` 为基准，默认写入 `data/recordings/sessions`。
- `auto_start` 适合固定诊断任务；日常开发建议通过 `recording-ctl` 显式控制。
- 完成会话包含 `manifest.json`、`vehicle_state.jsonl`、`events.jsonl`、`data_files.jsonl`
  和 `COMPLETE`。
- `manifest.json` 记录 project、schema_version、vehicle_id、config_path、config_checksum、
  git_commit、build_type、binary_version 和 sources，便于研发复盘。
- `recording-ctl --detail <session-id>` 可查看单个会话的 manifest 摘要和复盘元数据。
- `events.jsonl` 只接受合法 JSON value，并对 topic、manifest 和文件索引中的字符串统一转义。
- `data_files.jsonl` 只索引相机、音频、语音等大块数据文件的路径、source、kind、size 和
  checksum；`copy_into_session` 请求会把源文件复制到会话 `artifacts/`、记录相对路径并在未提供
  checksum 时自动生成 `fnv1a64`。
- `recording-ctl --verify <session-id>` 校验索引格式、路径边界、文件类型、大小和 checksum；当前
  支持 `fnv1a64`，空值和其他算法显示为 unavailable。
- `recording-ctl --report <session-id> --timeline-limit 100 --issue-limit 100 --output json`
  汇总 manifest、时间线、损坏行和 artifact 完整性；两类 limit 范围均为 1-1000，报告不健康时
  返回退出码 3。
- `recording-ctl --verify-all --from-started-ms 0 --to-started-ms 0 --limit 100 --output json`
  批量汇总会话完整性；时间范围包含端点，结束时间 0 表示不限制，limit 范围为 1-1000。存在
  damaged 或 unavailable 会话时返回退出码 3，单个会话失败不会中断整批。
- 异常退出遗留的 `.recording_*` 会在下次启动时改名为 `interrupted_*` 并写入
  `INTERRUPTED` 标记。
- 未启动录制时，`AppendEvent` 和 `AppendDataFile` 返回前置条件错误，不会伪装成成功。
- 当前已记录 VehicleState，并通过 `AppendEvent` 接收通用事件；camera 拍照文件会复制进当前会话，
  voice response 可写入 `events.jsonl`；camera status/frame metadata 通过 `camera_driver` 内部
  MessageBus 桥接到 recording 模块。音频大块数据源尚未接入。
- `max_sessions` 和 `max_total_bytes` 同时生效；完成会话后自动从最旧数据开始清理。
- `recording-ctl --prune` 按同一策略立即执行清理，不会删除当前活动会话。

## Navigator 运行策略

活动 YAML 不包含模块清单和依赖表。模块名、启动顺序、强弱依赖和 mode 组合的唯一来源是
`cockpit/navigator/run_config/run_config.cc`。旧 `runtime.dependencies` 及只展示它的
`cockpit-ctl dependencies` 已删除，避免业务配置和实际 Runtime 各维护一份策略。

## 语音和 AI

```yaml
features:
  voice:
    enabled: false
    asr_provider: mock
    asr_model_path: ""
    asr_language: zh
    asr_threads: 4
  ai:
    request_timeout_ms: 10000
```

启用 whisper.cpp：

```yaml
features:
  voice:
    enabled: true
    asr_provider: whisper_cpp
    asr_model_path: /cockpit-system/models/whisper/ggml-small.bin
    asr_language: zh
```

启用 sherpa-onnx + SenseVoice INT8：

```yaml
features:
  voice:
    enabled: true
    asr_provider: sherpa_onnx_sense_voice
    asr_model_path: /cockpit-system/models/sensevoice/model.int8.onnx
    asr_language: zh
    asr_threads: 2
```

SenseVoice 会在模型同目录读取 `tokens.txt`。ASR 只允许 `mock`、构建时可选的 `whisper_cpp` 或
`sherpa_onnx_sense_voice`，未知值会被配置校验拒绝。
`request_timeout_ms` 是一次 assistant 请求的交互层响应预算；当前 mock 用它判定超时并
丢弃迟到结果，真实 HTTP/gRPC provider 还必须把同一预算设置为网络 deadline，并实现 `Cancel()`，
不能依赖交互层强制终止阻塞的第三方调用。

## 未来配置契约

以下能力保留在规划中，但当前没有真实 consumer，因此字段名不进入活动 YAML，写入后会被严格
配置校验拒绝：

- WebSocket：候选职责是 gateway 的外部连接地址；实现 listener、鉴权和连接生命周期后再确定
  `services.gateway.websocket` 的最终结构。
- 云端上传：候选职责包括开关、broker、topic、QoS、设备身份、TLS、发布确认和重试；后端合同明确且
  `carupload` 建立真实 transport 后再确定 `services.cloud_uplink` 的最终结构。
- TTS 与交互模式：出现第二个真实 TTS provider 或 push-to-talk/wake-word 两种可切换实现后，再引入
  `features.voice.tts_provider` 或 `features.voice.mode`。
- LLM：真实 Assistant provider 接入并具备 deadline、取消和错误语义后，再引入
  `features.ai.provider` 与 `features.ai.model`。

`hardware.audio.capture_backend`、`hardware.audio.playback_backend`、`services.audio.vad.backend` 和
`services.camera.frame_transport` 也不作为当前配置。现阶段实现分别固定为 ALSA、energy VAD 和
POSIX shared memory；只有出现第二种可运行实现时才恢复选择字段。

## 配置原则

- 配置文件描述部署差异，不存放业务状态。
- 密钥和 token 不提交到仓库，未来使用环境变量或独立 secret 文件。
- 新增配置必须同步类型化结构、校验、示例和测试。
- 未知字段会携带完整 YAML 路径拒绝启动，避免拼错字段后静默使用默认值。
- 不允许模块自行重复解析 YAML。
