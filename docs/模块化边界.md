# 模块化策略

## 目标

保持一个主仓库，通过职责目录、独立 CMake target 和稳定接口实现内部模块化。进程级运行时参考
`zelos/znavigator` 的统一入口、动态模块和模式组合，但不照搬业务代号、全局对象和历史兼容层。

## 分层

```text
cockpit-system/
├── agent/         语音、会话、动作和本地 AI 应用层
├── cockpit/
│   ├── apps/       用户应用
│   ├── core/       通用基础设施
│   ├── drivers/    Linux/硬件适配
│   ├── library/    Navigator 加载的进程级业务模块
│   ├── modules/    平台无关领域能力
│   ├── navigator/  统一入口、进程管理和动态加载
│   └── proto/      跨进程契约
├── tools/          诊断和模拟器
├── tests/          单元与集成测试
└── scripts/        构建、运行和部署脚本
```

依赖方向：

```text
Linux / Hardware
       ↓
     drivers
       ↓
     modules
       ↓
library / agent / apps / tools

core 为 drivers 之上的项目层提供通用基础设施；drivers 不依赖任何 cockpit 项目层。
```

实际依赖按接口决定，禁止反向依赖：

- `core` 不依赖业务模块。
- `modules` 不依赖 process 或 app。
- `drivers` 只封装 Linux/硬件原始接口和类型，不包含业务策略，也不 include/link `core`、
  `modules`、`library`、Navigator 或 Agent。
- `modules` 可以使用 driver，将硬件原始类型适配为领域类型和逻辑。
- UI 不直接打开硬件设备。
- 进程级模块之间通过 `cockpit/proto` 定义的 gRPC 契约或明确 IPC 通信，不直接 include 对方实现。

## core

只存放跨领域基础设施：

- `config`：类型化配置。
- `event`：进程内事件。
- `ipc`：共享内存映射等通用 IPC。
- `logging`：日志。
- `runtime`：参数、信号和模块生命周期。
- `time`：主机时间戳。

禁止把暂时不知道放哪里的代码塞进 `cockpit/core/common/base/misc`。

## modules

领域代码必须能在没有长运行进程和真实硬件时测试。

```text
cockpit/modules/audio/
  frames/ capture/ playback/ transport/ wav/

cockpit/modules/camera/
  frames/ capture/ shared_memory/

cockpit/modules/voice/
  assistant/ actions/ responses/
```

领域子目录用于表达真实职责，由领域根目录的 `CMakeLists.txt` 集中声明 target。只有需要独立复用、
依赖隔离或条件编译的能力才建立 target，不为一两个文件机械增加叶子级 CMake 文件。调用方链接满足
需求的最小 target。

`can`、`vehicle` 等文件较少且职责单一的模块保持扁平，不为了目录对称而硬拆。

## library 与运行入口

`library/*` 表示进程级业务模块和资源所有权边界，不等于云端微服务。Navigator 为每个已启用模块
创建 module child，子进程通过版本化 C ABI 加载一个动态库。systemd 只守护 Navigator。

只有满足以下条件之一才建立独立进程：

- 独占硬件设备。
- 需要故障隔离。
- 有独立生命周期。
- 有真实部署边界。

当前真实模块：

- `transfer`
- `driver/vehicle`、`driver/audio`、`driver/camera`
- `agent`（薄 ABI 入口在 `cockpit/navigator/library/agent/`，实现在顶层 `agent/`）
- `hmi`（监管独立 Qt 主线程进程）
- `recording`
- `upgrader`
- `carupload`（仅有 ABI 骨架，上传 transport 尚未实现）

`debugger`、`calibration` 和 `watchdog` 当前也只有预留骨架，不进入产品 mode；出现真实资源所有权和
生命周期后再实现，不为了目录存在补空逻辑。

VAD、ASR adapter、intent parser 等是 Agent 进程内组件，不单独创建进程，也不各自做运行时
动态插件。真实算法在 Agent 产品构建中以普通 CMake target 组合；Navigator 模块动态库仍是唯一
进程级加载边界。

复杂模块按真实子域拆目录：

```text
cockpit/library/driver/audio/
  capture/ playback/ transport/ grpc/

cockpit/library/driver/camera/
  preview/ control/ grpc/

agent/
  runtime/ speech/ conversation/ interaction/ audio/ vehicle/ hmi/ grpc/
```

`entry.cc` 只暴露模块 ABI，真实装配放在同域 Runtime。Navigator 是长运行产品业务的唯一入口，
详细 smoke 也从 Navigator 启动真实模块组合，不再为每个模块维护独立 service main。

`ProcessRuntime` 仅用于诊断工具等独立可执行程序的参数、信号和退出；Navigator 管理进程级模块的
模式、启停、重启和查询。
不要为了统一形式把纯数据类、解析函数或同步业务对象包装成 Runtime 或 Module。

Qt UI 保留标准 `QGuiApplication::exec()` 主线程。HMI Runtime 只拥有 UI 子进程的启动、退出和故障
状态，不把 Qt event loop 塞进 module ABI `poll()`，也不把这段单用途生命周期抽成通用 process helper。

模块标识、mode 标识、模块到动态库的映射和 mode 到模块集合的映射属于编译期产品策略，集中在
`navigator/run_config`，不写入业务 YAML。内部使用 `ModuleId` 和 `RunMode`，只在 CLI/IPC 边界
解析字符串。生产由唯一的 `cockpit-navigator.service` 固定从 normal mode 启动；systemd 不描述
业务组合，也不为 development/cloud 维护额外 unit。

`ModuleId` 和 `RunMode` 使用显式固定数值，新增成员只能分配新值，不能因调整声明顺序改变已有值。
Navigator 启动前统一校验 run config：Unix Socket 必须是绝对路径，动态库必须是模块目录下的
`.so` 文件名，模块和 mode 不得重复，mode 不得引用未配置模块，超时和重启策略必须有效。产品策略
配置错误时直接拒绝启动，不带着部分配置继续运行。

重启策略属于模块，不属于整个 Navigator。每个模块分别声明是否关键、时间窗口内的重启上限和
重启延迟；延迟由 Navigator 事件循环调度，不阻塞 IPC。硬件驱动、transfer、agent 和 upgrader
属于关键模块，耗尽重启次数后 Navigator 失败退出，由 systemd 在进程边界恢复；HMI、recording
和当前预留模块失败时保持可诊断的 `failed` 状态，不拖垮 normal mode。

## CMake target

命名使用简短职责名：

```text
config logging runtime ipc
audio_frames audio_capture audio_stream_protocol audio_wav
camera_frames camera_capture camera_shm
agent_speech voice_actions voice_responses
```

避免 `cockpit_common_runtime` 这类冗长名称。每个 target 声明自己的直接依赖，不依赖全局 link
状态。

## 通信规则

- 同线程：函数调用。
- 同进程低频：callback/EventQueue。
- 同进程音频连续流：SPSC RingBuffer。
- Audio Driver 到 Agent 的 PCM：Unix `SOCK_SEQPACKET` 固定协议。
- 相机大帧：shared memory。
- 控制、状态和文本：gRPC。
- 云端：未来 MQTT/WebSocket。

不把 PCM、图片或未来点云直接放进 gRPC。

## 何时增加抽象

只有至少两个真实调用方出现相同需求时，才增加通用 Actor、MessageBus、Scheduler、Recorder、
Monitor 或插件框架。不要先创建空接口等待未来使用。

模块边界不等于把每段短逻辑做成 helper 或类。单次、短小且没有独立资源/协议边界的逻辑优先留在
调用处；具体判断标准见 [代码风格](代码风格.md) 的“克制抽象”。

## 何时拆仓

当前只维护 `cockpit-system`，负责 Jetson 车端车辆、音频、语音、相机、UI、诊断和部署。完整云
平台、生产 Web 前端、车队管理、自动驾驶算法、Android 虚拟化和量产级安全不属于当前范围。

只有同时出现以下条件时才考虑拆仓：组件可独立部署、具有独立版本周期、跨仓协议稳定、维护责任或
技术栈明确，并且独立 CI/CD 的收益高于同步成本。未来可能形成 `cockpit-cloud`、`cockpit-web`，
`cockpit-proto` 只有在协议真正稳定后才可能独立；现阶段不创建空仓库。

如确实需要历史展示，云端先保持最小范围：接收车辆状态、保存 SQLite/PostgreSQL、查询最近状态和
历史曲线、提供简单设备鉴权，不直接建设完整车联网平台。真实部署边界决定仓库边界。
