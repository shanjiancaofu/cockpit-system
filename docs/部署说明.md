# Jetson 构建与部署

cockpit-system 参考 zelos/znavigator 的思路，将源码、构建、安装暂存、发布包和车端运行目录
分开：

```text
源码 -> _output/build/<架构>-<类型> -> _output/install/stage -> _output/install/dist/*.tar.gz
     -> /cockpit-system
```

## 构建目录

```text
_output/
├── build/
│   ├── x86_64-debug/
│   ├── x86_64-release/
│   ├── arm64-debug/
│   └── arm64-release/
├── install/{stage,dist}/
└── runtime/{data,logs,reports}/
```

## 工具链职责

| 场景 | 工具链 | 配置入口 | 产物用途 |
|---|---|---|---|
| VS Code 代码解析 | `/usr/bin/c++` + Debug compile database | `.vscode/settings.json` | 仅用于 IntelliSense，不决定真实编译器 |
| WSL 日常开发 | GCC Debug | `scripts/build.sh` | 编译诊断、CTest、smoke 和 clang-tidy |
| Linux 正式构建 | GCC Release | `scripts/build.sh --type release` | x86_64 发布包和正式构建基线 |
| Jetson 交叉构建 | `aarch64-linux-gnu-g++` + Jetson sysroot | `cmake/toolchains/jetson-aarch64.cmake` | WSL 生成 ARM64 Release 产物 |
| Jetson 原生构建 | Jetson 系统 GCC Release | `scripts/build.sh --arch arm64 --type release` | 实机最终兼容性确认 |

编译器选择只由构建入口和 CMake toolchain 决定。IDE 的 `compilerPath` 不参与打包；CMake 会把实际
编译器、目标平台和依赖版本写入 `package-info.env`，打包脚本只消费这个稳定接口。

WSL/Ubuntu 日常开发：

```bash
bash scripts/build.sh                                  # GCC Debug
bash scripts/build.sh --arch x86_64 --type release    # GCC Release
```

在 Jetson 上执行相同脚本时，默认目录是 `_output/build/arm64-debug`：

```bash
bash scripts/build.sh                                  # GCC Debug
bash scripts/build.sh --arch arm64 --type release     # GCC Release
```

开发检查使用 GCC Debug 的 compile database；正式 Linux 构建、Jetson 交叉构建和发布包使用 GCC
Release。`clang-tidy` 只负责静态检查，不作为项目编译器。`scripts/package.sh` 会校验 CMake 记录的
编译器，拒绝将非 GCC 构建误打成正式包。

项目固定构建 HMI、GStreamer 和 sherpa-onnx + SenseVoice。模型测试资源仍通过额外 CMake 参数传入：

```bash
bash scripts/build.sh --arch arm64 --type release -- \
  -DSHERPA_ONNX_SENSEVOICE_MODEL_PATH=/path/to/model.int8.onnx \
  -DSHERPA_ONNX_SENSEVOICE_TEST_WAV_PATH=/path/to/16k-mono.wav
```

正式构建可省略两个测试资源参数。项目协议与 gRPC 使用 Ubuntu 22.04 系统安装的 Protobuf 3.12.4；
Sherpa-ONNX 源码路径可通过 `COCKPIT_SHERPA_ONNX_SOURCE_DIR` 覆盖。Sherpa-ONNX 自己管理
ONNX Runtime，不与项目 gRPC 强行共用 Protobuf。

## WSL 交叉编译 ARM64

交叉编译需要 `aarch64-linux-gnu-g++`、与目标 Jetson 完全匹配的 JetPack/L4T sysroot，
以及 sysroot 中 ARM64 版本的 Qt、ALSA、GStreamer、gRPC、protobuf 和 yaml-cpp。启用 CUDA
时还需要匹配版本的 Jetson CUDA 头文件和目标库。

```bash
sudo apt-get install -y g++-aarch64-linux-gnu rsync

bash scripts/prepare_jetson_sysroot.sh \
  --source ffz@JETSON_IP \
  --output toolchains/jetson-sysroot

JETSON_SYSROOT="$PWD/toolchains/jetson-sysroot" \
  bash scripts/build.sh --arch arm64 --type release
```

需要 CUDA 时给 sysroot 脚本添加 `--with-cuda`。CUDA 目录较大，因此默认不复制。

工具链文件位于 `cmake/toolchains/jetson-aarch64.cmake`。交叉构建不运行 CTest，因为 ARM64
程序不能直接在 x86_64 WSL 中执行。当前优先推荐 Jetson 原生构建；CUDA、TensorRT 和
Jetson 多媒体库与 JetPack 版本绑定较强，原生构建更稳定。

### 版本与边界

- 交叉编译器、sysroot 和目标运行库必须兼容；不确定时使用与目标系统一致的编译环境或 Jetson 原生构建。
- CMake、Ninja、`protoc` 和 `grpc_cpp_plugin` 使用 WSL 宿主程序；Qt、ALSA、GStreamer、gRPC、protobuf、
  yaml-cpp、CUDA 和 TensorRT 的头文件与库必须来自目标 sysroot。
- `toolchains/jetson-sysroot/` 是机器生成物且不进入 Git；`SYSROOT_INFO` 记录来源、生成时间和 CUDA 状态。
- ARM64 产物不能在 WSL 直接执行，WSL 只做配置、编译、链接、ELF 架构和发布包完整性检查。

### 验收顺序

1. 从最终目标 Jetson 准备 sysroot，并确认 JetPack/L4T 与车辆目标环境一致。
2. 在 WSL 完成 ARM64 GCC Release 构建和打包，确认 ELF 为 AArch64，发布清单记录 GCC 与 arm64。
3. 将同一发布包安装到 Jetson，检查动态库解析、systemd 启动、健康检查和 rollback。
4. 再验证 ALSA、CSI/GStreamer、CAN、CUDA/TensorRT 和持续运行；通过后才把交叉构建列为正式交付路径。

## 打包

脚本默认选择当前机器对应的 Release 目录，也可以显式指定：

```bash
bash scripts/package.sh
BUILD_DIR=_output/build/arm64-release bash scripts/package.sh
```

包名中的架构读取 CMake 目标架构，不使用构建机的 `uname -m`。所以在 x86_64 WSL 中交叉
编译得到的包仍命名为 `linux-arm64`。

```text
_output/install/stage/cockpit-system-<version>-<system>-<arch>/
_output/install/dist/cockpit-system-<version>-<system>-<arch>.tar.gz
```

SenseVoice 模型不进入程序包，避免每次升级重复传输大文件。

## 车端目录

```text
/cockpit-system/
├── current -> releases/0.1.0
├── releases/0.1.0/{bin,lib,share}
├── config/config.yaml
├── models/sensevoice/{model.int8.onnx,tokens.txt}
├── data/
├── logs/
└── run/
```

安装和启动：

```bash
tar -xzf cockpit-system-*.tar.gz
cd cockpit-system-*
sudo bash deploy/install.sh
sudo systemctl enable --now cockpit.target
```

安装脚本由管理员通过 `sudo` 执行，并创建无登录、无密码的 `cockpit` 系统用户运行 Navigator。
该用户仅加入机器上已有的 `audio`、`video`、`render` 和 `dialout` 设备组。部署过程不读取、不保存
管理员或 Jetson 桌面用户的密码；SSH 登录认证由机器自身的密钥或账号策略管理。

启动组合：

```bash
# normal：transfer、三类 driver 和 agent；默认不启动 UI
sudo systemctl enable --now cockpit.target

# development：normal + recording
sudo systemctl enable --now cockpit-development.target

# cloud：transfer + vehicle_driver + carupload
sudo systemctl enable --now cockpit-cloud.target
```

三个 target 互斥，每个 target 只托管一个 `cockpit-navigator@<mode>.service`。切换已运行系统的
模块组合也可以使用 `cockpit-ctl runtime switch <mode> --socket /cockpit-system/run/navigator.sock`。
发布包不再包含旧的独立 service 二进制；安装脚本仍会停用并删除历史 unit，避免升级后残留进程占用
端口或硬件。

HMI 和 `cockpit-ui` 仍参与构建，但不加入任何 systemd 默认 target。Jetson 图形栈完成长稳验证前，
不要在开机流程中启动 UI；需要临时验证时可显式切换：

```bash
sudo /cockpit-system/current/bin/cockpit-ctl runtime switch ui \
  --socket /cockpit-system/run/navigator.sock
```

模型单独安装：

```bash
sudo install -m 0644 model.int8.onnx /cockpit-system/models/sensevoice/model.int8.onnx
sudo install -m 0644 tokens.txt /cockpit-system/models/sensevoice/tokens.txt
```

检查、回滚和不修改系统的安装模拟：

```bash
sudo bash deploy/healthcheck.sh
sudo bash deploy/rollback.sh 0.1.0
sudo systemctl restart cockpit.target

COCKPIT_ROOT=/tmp/cockpit-system-test INSTALL_SYSTEMD=false bash deploy/install.sh
```

`install.sh` 在写入 release 前先用设备信任的 Ed25519 公钥验证
`manifest/SHA256SUMS.sig`，再校验包内 `SHA256SUMS`。`healthcheck.sh` 从 Navigator 查询当前 mode，
同时校验 Navigator 和全部 module child 都来自当前 release，再检查模块状态和 gRPC health；
normal mode 不会把未启动的 recording 当作部署失败。

WSL 上可一次执行配置、Release 打包、临时安装和故障恢复矩阵：

```bash
bash scripts/run_wsl_matrix.sh
```

退出码表示整体结果，机器可读报告写入 `_output/runtime/reports/wsl-matrix.json`。

## 诊断快照

系统异常时可一次收集模块接口状态、Navigator Runtime 状态、构建信息和有界日志尾部：

```bash
/cockpit-system/current/bin/cockpit-ctl snapshot \
  --config /cockpit-system/config/config.yaml \
  --socket /cockpit-system/run/navigator.sock \
  --max-snapshots 10 \
  --max-total-bytes 104857600
```

默认输出到 `paths.data_dir/diagnostics/snapshot-<timestamp_ms>`，也可用 `--directory` 指定目录，用
`--max-log-bytes` 限制每份日志最多复制的字节数。归档包含 `manifest.json`、`service_status.json`、
`runtime_status.txt` 和 `logs/`；部分模块或 Navigator 离线时仍会生成快照并记录错误。工具最多收集
32 个最新 `.log` 文件，当前文件名包含模块和切分时间，同时兼容归档旧版 `.log.1`。快照先写 `.partial`
目录再原子发布，不复制完整配置文件，避免将后续加入的令牌或证书带入诊断归档。

默认最多保留 10 份快照、合计 100 MiB，超过 `--max-snapshots` 或 `--max-total-bytes` 后按修改时间
删除同目录中最旧的 `snapshot-*`。`run_navigator_stability.sh` 在 Navigator 未就绪、健康采样失败、
故障恢复失败、进程退出或脚本异常时只抓取一次，并把原因、是否成功、快照路径和 Navigator 日志路径
写入稳定性报告；健康运行不会生成快照。

Navigator 对运行中 module child 的异常退出另外生成结构化记录，默认位置为
`paths.data_dir/crashes/crash-<timestamp_ms>-<pid>.json`。记录包含退出码或 signal、是否产生 core、
重启是否成功和替代进程 PID，最多保留 20 份；正常停止、显式重启和 mode 切换不生成记录。该目录
只保存元数据，不保存 core、配置或完整日志。

稳定性脚本支持 `--fault-count` 重复注入故障。schema 3 报告在每个样本中分别记录 Navigator 和运行中
module child 的 RSS、线程数及 FD 数，并汇总整体初值、峰值和结束值；同时统计 logs、recordings、
reports 和 diagnostics snapshots 的目录字节数。资源样本不可用时检查失败，不用 `pid=0` 的未启动
预留模块制造假告警。

```bash
bash scripts/run_navigator_stability.sh \
  --duration 300 --interval 5 --mode development \
  --fault crash --module camera_driver --fault-count 3
```

## Safe OTA 原型

发布私钥只能保存在受控构建环境，不能进入仓库或发布包。首次部署前生成密钥并把公钥预置到设备：

```bash
openssl genpkey -algorithm ED25519 -out ota-signing-key.pem
openssl pkey -in ota-signing-key.pem -pubout -out ota-public-key.pem
sudo install -m 0444 ota-public-key.pem /cockpit-system/config/ota-public-key.pem

OTA_SIGNING_KEY="$PWD/ota-signing-key.pem" bash scripts/package.sh
```

`safe-ota` 接收解压后的候选发布包，操作前必须显式确认包内版本：

```bash
sudo /cockpit-system/current/bin/safe-ota \
  --package /cockpit-system/data/ota/incoming/cockpit-system-0.2.0-linux-arm64 \
  --confirm 0.2.0 \
  --root /cockpit-system \
  --socket /cockpit-system/run/navigator.sock
```

工具在执行包内任何脚本前验证 Ed25519 签名、checksum、确认版本和单调版本策略，请求 Navigator
进入只运行 upgrader 的 `upgrade` mode，将候选安装到 `releases/<version>` 并原子更新 `current`。
激活后 Navigator 通过 `exec` 替换为新 release，全部 module child 和 UI 重新启动；健康检查确认整棵
进程树均来自新 release 后才写入 `data/ota-version-floor` 并确认升级。旧版本或相同版本的合法签名包
也会被 anti-rollback 拒绝。健康检查失败时恢复旧版本、删除失败版本并重新执行旧 Navigator。WSL 或
救援环境可加 `--standalone`，不通过 Navigator 执行同一安装和回滚事务。
在线模式只接受 `/cockpit-system/data/ota/incoming`（0700）内的候选包，使 systemd
`PrivateTmp` 和 `ProtectHome` 保持生效；只有显式 `--standalone` 的救援流程可从其他目录安装。

安装前会写入 `run/upgrade-transaction.yaml`，记录 `prepared`、`activated`、`confirmed` 阶段。事务
使用“临时文件写入并 fsync -> rename -> 父目录 fsync”的顺序发布；安装脚本在切换 `current` 前同步
候选内容，切换和回滚后再次同步安装根目录。这样重启后可以根据最后一个完整事务状态决定回滚未确认
版本，或保留已 confirmed 版本。

`run/safe-ota.lock` 保证同一安装根目录只执行一个升级。systemd 在 Navigator 启动前执行一次
`safe-ota --recover`，因此开机和服务重启会先收口遗留事务；救援流程也可显式执行：

```bash
sudo /cockpit-system/current/bin/safe-ota --recover --root /cockpit-system
```

当前自动测试覆盖 prepared 切换前后、activated、confirmed、签名/内容篡改、anti-rollback、卡死健康
检查进程组清理、新旧完整进程树切换和失败回滚。尚未用真实 Jetson 存储介质做拔电测试，也未覆盖 A/B
分区、systemd unit 替换和 Jetson 重启后确认。设备身份、后端发布授权、密钥轮换/吊销和车辆升级安全
条件仍需配合后端协议统一设计，因此该实现仍不能宣称为量产安全 OTA。

### Safe OTA 后续演进

后续参考 zelos safe_ota 的职责分层，但只在出现真实产品需求时增加对应目录。目标结构是：

```text
tools/safe-ota/
  main.cc                   # 参数、环境初始化和启动装配
  common/                   # 稳定选项、状态枚举和错误语义
  action/                   # 升级安全编排，必要时容纳不同车型实现
  state/                    # 真实车辆升级条件快照
  table/                    # 多线程查询的进程内运行状态
  restful/                  # 仅当 Safe OTA 成为受控常驻协调器时考虑
```

`state/`、`table/` 和 `restful/` 目前不创建空骨架。它们的启用条件和边界如下：

1. **车辆安全条件**：当档位、车速、电量、充电、上下电等正式信号合同确定后，在
   `state/` 实现可读的升级条件快照。Safe OTA 只通过 vehicle/transfer 合同取数，不直接读 CAN
   frame；任一必需信号缺失、过期或不满足时禁止激活候选版本。
2. **运行状态查询**：当 UI、Navigator 和远程接口需要并发查询进度时，在 `table/` 保存
   idle、precheck、prepared、activated、validating、confirmed、rolling_back 和 failed 等进程内状态，
   以及进度、原因和更新时间。它只是查询投影；`run/upgrade-transaction.yaml` 仍是进程中断恢复的
   唯一持久化事实，不建立第二份事务状态源。
3. **多车型 action**：只有至少两种真实流程出现差异，例如多 ECU 心跳、下电管理或底盘协同时，
   才在 `action/` 引入共同接口和 factory。车型由受信任设备配置决定，不允许远程请求任意选择
   action 绕过本车安全规则。
4. **远程接口**：后端协议确定后，默认由 transfer 提供 HTTPS/gRPC 控制面，并实现 CA 链、双向
   TLS、设备身份、发布授权、防重放和审计。远程请求只能提交、查询或取消升级意图，不能直接
   修改 symlink、运行安装脚本或跳过本地安全检查。只有 Safe OTA 未来独立变为受控常驻进程时，
   才评估是否需要自有 `restful/`，不与 transfer 重复建立外部接口。

实施顺序为：先完成 Jetson 启动恢复和断电持久性，再接入车辆安全条件，然后根据真实车型差异扩展
action/factory，最后与后端 PKI 和发布协议一起开放远程控制面。在前一阶段没有可重复验证前，不启用后一阶段。

开发目录中也可以直接执行本机健康检查：

```bash
bash scripts/check_health.sh
```

systemd 只负责 Navigator 的进程级存活和模式选择。模块启动顺序、故障重启、状态和退出回收由
Navigator 管理；模块间业务依赖仍通过 gRPC 合同和弱依赖重连处理。

## 依赖策略

默认发布包使用系统提供的 Qt、ALSA、gRPC、Protobuf 3.12.4、yaml-cpp、GStreamer 和平台库，
不重复打包这些系统运行库。Sherpa-ONNX 与 ONNX Runtime 的静态依赖留在 audio 模块内部。
模型和 `tokens.txt` 独立放入 `/cockpit-system/models/sensevoice/`。
